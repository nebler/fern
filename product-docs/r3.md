# Fern Outside-In Product Audit

> Historical audit. See [`product-docs/README.md`](./README.md) before using any
> finding as current product or implementation guidance.

> Post-audit update (2026-08-16): Fern now has process-local one-time phone
> pairing, `/fern/*` landing/readiness routes, `fern init`, `fern doctor
> --phone`, and an explicit host-only draft-PR publication prototype. Historical
> findings below describe the audited snapshot; durable device identity,
> GitHub App onboarding, notifications, and real-phone acceptance remain open.

> From my phone, connect a private repository, ask an agent to make a change,
> let it work while I disconnect, answer any questions or permissions, inspect
> the result, and receive a tested draft pull request. Later, handle CI failures
> or review feedback, survive sleep and reboot, and restore the workspace after
> host loss.

## Verdict

Fern cannot complete this outcome today.

Fern implements a careful authenticated wake/sleep boundary around one
pre-existing host directory. The released OpenCode V2 server supplies
the official web UI that Fern should expose unchanged at `/`; Fern does not
implement the surrounding remote-agent product: device auth, repository
onboarding, durable shadow operations,
approval delivery, result review, Git publication, CI continuation, reboot
recovery, or complete restoration.

The repository states this accurately in `README.md` and
`docs/REMOTE_PRODUCT.md`.

The V2-only architecture direction is not implementation evidence. Device
pairing, a browser cookie gateway, notifications, tested publication,
attach-existing-service mode, and real-phone validation are proposed or
unperformed, not implemented.

## Status Language

- **Implemented:** Executable first-party behavior exists.
- **Documented:** A procedure exists, but Fern does not execute it.
- **Delegated:** Another product owns behavior through a concrete integration.
- **Assumed:** Fern requires external behavior but supplies no complete integration.
- **Unsupported:** The current system cannot provide the required guarantee.
- **L0:** The core outcome cannot complete without it.
- **L1:** The outcome works, but is unreliable, unsafe, or painfully manual.
- **L2:** Differentiation that materially improves Fern after all L0 gaps close.
- **Later:** Scale or enterprise functionality unnecessary for the first user.

## End-To-End Trace

### 1. Install And Maintain The Server

1. **User action:** Provision Ubuntu, install Docker, Git, Go, and Tailscale;
   create a UID/GID 1001 service account; clone Fern; select a commit; compile
   it; build an image; install configuration and secrets; install systemd; and
   configure Tailscale Serve.
2. **Owner:** The operator owns almost the entire installation. Fern owns
   runtime startup only after installation succeeds.
3. **Identity and credentials:** Root or sudo, Docker-group access, Git access,
   Tailscale identity, a provider key, and an OpenCode Basic password.
4. **Credential location and lifetime:** Provider and OpenCode credentials live
   in `/etc/fern/fern.env`, then in the Fern process and Docker container
   environment. Tailscale credentials are external. Fern has no expiry or
   rotation workflow.
5. **Durable proof:** The installed binary, source checkout, local image,
   `/etc/fern`, systemd unit, Tailscale configuration, and host logs. Fern has
   no installation manifest or attestation record.
6. **Failure behavior:** Each step is a shell procedure. There is no transaction,
   rollback, resumable installer, or idempotent preflight. Configuration or
   credential changes can cause spec drift and require manual `down` and `up`.
7. **Observe, retry, cancel, recover:** Use `systemctl`, `journalctl`, Docker,
   Tailscale, and manually rerun commands.
8. **Status:** Documented and manual, not productized. **L0.**
9. **Evidence:** `docs/DEPLOYMENT.md` explicitly says the complete install,
   remote access, reboot, backup, and restore sequence has not been executed.
10. **Leading products:** Managed Codex, Jules, Copilot, Cursor, and Devin remove
    host installation. Mature self-hosted products generally provide a package
    or installer, preflight, health checks, and an update/rollback path.

### 2. Pair A Phone Or Browser And Reconnect

1. **User action:** Enroll the server and phone in one tailnet, configure
   Tailscale Serve, discover the URL, and open the official OpenCode V2 web UI
   proxied unchanged at `/`.
2. **Owner:** OpenCode owns the user-facing UI, sessions, configuration,
   providers, and protocol behavior. Tailscale owns reachability, and Fern owns
   wake-aware authenticated reverse proxying plus future `/fern/*` controls.
3. **Identity and credentials:** Tailscale account/device identity plus one
   shared OpenCode Basic password.
4. **Credential location and lifetime:** Tailscale-managed device credentials
   and a manually distributed long-lived password. Fern has no device session,
   refresh, selective revocation, or recovery model.
5. **Durable proof:** Tailscale state exists outside Fern. Fern records no paired
   device, login, client session, last connection, or revocation.
6. **Failure behavior:** Fern has no delivery queue when the phone disconnects.
   An SSE-only reconnect does not wake paused compute; another read or work
   request is required.
7. **Observe, retry, cancel, recover:** Use the official OpenCode UI and external
   Tailscale diagnostics. Fern has no pairing, cookie, or notification routes.
8. **Status:** Official UI proxying is the V2-only direction; device pairing,
   cookie gateway, notifications, attach-existing-service mode, and mobile
   acceptance are proposed/unproven. **L0.**
9. **Evidence:** The official UI has not been tested through Fern on a phone.
   Remote phone access is explicitly unproven in
   `docs/ARCHITECTURE.md`. Observation behavior
   is implemented in `internal/proxy/proxy.go` and
   `internal/workspace/manager.go`.
10. **Leading products:** GitHub Copilot supports GitHub Mobile task creation and
    tracking. Claude Remote Control provides iOS, Android, and web clients,
    session links and QR codes, short-lived credentials, push notifications,
    reconnect state, and device revocation. Jules and Codex provide browser
    task surfaces.

### 3. Authenticate A Provider, Select A Model, And Set A Budget

1. **User action:** Obtain an API key externally, put it in the host environment
   file, and use OpenCode V2 configuration and UI for provider and model
   selection.
2. **Owner:** The provider authenticates the key. OpenCode selects and invokes
   the model. Fern forwards environment variables.
3. **Identity and credentials:** `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, or
   arbitrary values under `workspace.env`.
4. **Credential location and lifetime:** Plaintext systemd environment, Fern
   process environment, and Docker container configuration. Fern does not know
   expiry, quota, scope, or rotation state. Rotation requires recreation.
5. **Durable proof:** The container spec fingerprint changes, but Fern has no
   provider account, selected model, quota, cost, or task-usage record.
6. **Failure behavior:** Invalid, expired, exhausted, and rate-limited keys
   surface only through OpenCode. Fern cannot normalize provider outage, model
   removal, quota exhaustion, or budget exhaustion.
7. **Observe, retry, cancel, recover:** Inspect upstream output and raw logs,
   replace the key manually, run `fern down`, and restart.
8. **Status:** Delegated without product integration. **L0.**
9. **Evidence:** Provider-backed scenarios are explicitly `NOT_RUN` in
   `integration/artifacts/20260816T180937Z-21024-22784/run.txt`.
10. **Leading products:** Copilot, Codex, and other managed agents expose model
    selection, entitlement, usage, and billing behavior. They reject or stop
    work when the configured plan, quota, or execution limit is exhausted.

### 4. Connect GitHub And Select One Private Repository

1. **User action:** Today, manually authenticate Git on the host and clone the
   repository into the configured path. Proposed commands such as
   `fern github connect` and `fern workspace create` do not exist.
2. **Owner:** The operator and host Git currently own this. The proposed future
   owner is a Fern host-side GitHub App broker.
3. **Identity and credentials:** Currently unspecified Git credentials. The
   design proposes a GitHub App key, installation ID, repository ID, App JWT,
   and one-hour installation token.
4. **Credential location and lifetime:** No supported current storage. A token
   placed in `workspace.env` is exposed to the container. The proposed host-only
   token lifecycle is documentation only.
5. **Durable proof:** A host directory and `.git` metadata. Fern records no
   installation, immutable repository ID, selected permissions, base SHA, or
   revocation state.
6. **Failure behavior:** Clone and authentication failures are shell failures.
   Removed installations, changed permissions, renamed repositories, and lost
   callbacks have no Fern recovery path.
7. **Observe, retry, cancel, recover:** Manual Git commands and GitHub dashboard
   inspection.
8. **Status:** Design documented, not implemented. **L0.**
9. **Evidence:** `docs/GITHUB_INTEGRATION.md` says the design is not
   implemented. `cmd/fern/main.go` has no GitHub command.
10. **Leading products:** Codex, Jules, Cursor, and Copilot provide GitHub
    OAuth/App installation, selected-repository authorization, and repository
    selectors.

### 5. Clone Exact Source And Prepare The Project

1. **User action:** Clone manually, ensure UID compatibility, initialize
   submodules and LFS, install dependencies, and expose registry credentials.
2. **Owner:** Host Git and commands run by OpenCode. Fern only bind-mounts a
   directory.
3. **Identity and credentials:** Git, submodule, LFS, registry, SSH host trust,
   and private-network credentials.
4. **Credential location and lifetime:** Unspecified. `workspace.env` exposes
   credentials for the full container lifetime and through Docker inspection.
5. **Durable proof:** Repository files persist. Setup completion, setup version,
   dependency state, cache key, and credential scope do not.
6. **Failure behavior:** Partial clone, missing LFS content, failed setup, token
   expiry, lockfile change, and interrupted dependency installation are
   indistinguishable from an agent failure. Most home caches disappear when the
   container is recreated.
7. **Observe, retry, cancel, recover:** Raw output and manual shell repair. There
   is no setup status or reset operation.
8. **Status:** Assumed. **L0.**
9. **Evidence:** `runtime.Spec` has only name, image, repository, memory, and
   environment. Docker mounts only the repository and OpenCode
   data in `internal/runtime/docker.go`. Images do not install Git LFS.
10. **Leading products:** Codex checks out a branch or SHA, runs setup and
    maintenance scripts, separates setup-only secrets from the agent phase, and
    caches environments. Copilot supports `copilot-setup-steps.yml`; Jules
    supports environment setup scripts.

### 6. Submit Durable Work And Disconnect

1. **User action:** Use the official OpenCode UI to send a live HTTP request.
   Fern does not create a competing task object.
2. **Owner:** OpenCode owns the session and provider turn. Fern owns request
   admission and proxy lifetime only.
3. **Identity and credentials:** Shared Basic authentication plus the provider
   key inside the workspace.
4. **Credential location and lifetime:** Long-lived environment values. There
   is no task-scoped credential.
5. **Durable proof:** OpenCode may persist completed session content. Fern
   records no correlated lifecycle/publication operation, delivery
   acknowledgement, attempt, deadline, or result provenance.
6. **Failure behavior:** A lost response cannot distinguish not submitted,
   submitted, applied, or completed. A retry can duplicate work. Client
   disconnect continuation is upstream-dependent and untested. HTTP cancellation
   is not durable task cancellation.
7. **Observe, retry, cancel, recover:** Reconnect to OpenCode and infer state.
   Fern has no inbox, task list, retry, or cancellation API.
8. **Status:** OpenCode session submission exists; durable Fern shadow semantics
   for lifecycle and external effects are unsupported. **L0.**
9. **Evidence:** `internal/workspace/manager.go` tracks only live request
   admission. The Docker fixture does not execute provider-backed work.
10. **Leading products:** Copilot, Codex, Jules, Cursor, and Devin create durable
    task/session objects visible after disconnect. Claude Remote Control stores
    transcript state and queues status updates while reconnecting.

### 7. Answer Questions And Permission Requests

1. **User action:** Stay attached to an OpenCode client and notice the prompt.
   Fern provides no notification or approval surface.
2. **Owner:** OpenCode creates and resolves permissions and forms. Fern only
   checks whether pending V2 requests exist before sleeping.
3. **Identity and credentials:** Shared Basic authentication, with no approver
   identity or step-up authorization.
4. **Credential location and lifetime:** Upstream OpenCode state. Fern stores no
   approval, answer, actor, expiry, or policy.
5. **Durable proof:** None in Fern. A pending request merely prevents idle stop.
6. **Failure behavior:** There is no notification, expiry, lost-response
   reconciliation, duplicate-answer protection, or safe default.
7. **Observe, retry, cancel, recover:** Use an upstream client. Fern cannot list
   or answer approvals.
8. **Status:** Observed only as a sleep blocker. **L0.**
9. **Evidence:** `watch.AllSessionsIdle` includes V2 permission and form
   endpoints at `internal/watch/status.go:19-29`. Tests prove only that they
   block pause.
10. **Leading products:** Claude Remote Control forwards permission questions to
    web/mobile, sends push notifications, preserves questions until answered,
    and documents dialog expiry. Jules notifies users when input is required.

### 8. Observe Logs And Take Over

1. **User action:** Run `fern logs` on the host or rely on the OpenCode TUI.
2. **Owner:** Docker owns container logs, OpenCode owns tool output, and Fern
   exposes raw Docker log streaming.
3. **Identity and credentials:** Host shell/Docker access or shared Basic auth.
4. **Credential location and lifetime:** Fern has no viewing session or terminal
   ownership lease.
5. **Durable proof:** Docker logs exist subject to external rotation. Fern has no
   structured command or event journal.
6. **Failure behavior:** Logs may rotate, leak secrets, lose correlation, or
   disappear with host loss. Terminal disconnect has no safe handoff protocol.
7. **Observe, retry, cancel, recover:** Re-run `fern logs` or manually attach.
8. **Status:** Raw logs implemented; remote worklog and takeover absent. **L1.**
9. **Evidence:** `cmd/fern/commands.go` and
   `internal/runtime/docker.go` delegate logs directly to Docker.
10. **Leading products:** Devin provides a durable progress feed, command
    history, IDE, browser, read-only terminal observation, and explicit writable
    takeover. Jules exposes an activity feed and per-file mini-diffs.

### 9. Inspect Diff, Tests, Artifacts, And Previews

1. **User action:** Infer changes through an upstream client or inspect the host
   repository and rerun tests manually.
2. **Owner:** Git and OpenCode produce raw information; no Fern component
   packages or preserves it.
3. **Identity and credentials:** Repository access and shared Basic auth.
4. **Credential location and lifetime:** Files persist, but test outcomes and
   artifacts have no Fern authorization or retention model.
5. **Durable proof:** No immutable base/head diff, test command/result, artifact
   digest, preview URL, or completion attestation exists.
6. **Failure behavior:** A claimed test may not have run, output may be
   truncated, files may change after testing, and artifacts cannot survive host
   loss through Fern.
7. **Observe, retry, cancel, recover:** Manual Git inspection and test reruns.
8. **Status:** Absent. Diff and test results are **L0**; general artifacts and
   previews are **L1**.
9. **Evidence:** No artifact, result, diff, or preview API exists.
   `docs/REMOTE_PRODUCT.md` marks the boundary blocked.
10. **Leading products:** Codex shows logs, summary, diff, and follow-up controls.
    Jules provides an activity feed, full diff editor, summary, and publication.
    Devin supports IDE/browser verification and screenshots or recordings.

### 10. Commit, Sign, Push, And Create A Draft PR

1. **User action:** Manually configure Git identity and credentials, create a
   branch, commit, push, and create a PR.
2. **Owner:** Currently the user and container Git. The documented design assigns
   publication to a Fern host broker.
3. **Identity and credentials:** Commit author/committer identity, optional
   signing key, and a GitHub installation token or PAT.
4. **Credential location and lifetime:** None configured. A PAT in the container
   is long-lived and exposed. The proposed one-hour in-memory installation token
   flow is unimplemented.
5. **Durable proof:** Local Git and remote GitHub objects if manually created.
   Fern records no operation ID, branch, commit OID, expected remote SHA, or PR.
6. **Failure behavior:** Ambiguous push results, non-fast-forward updates,
   signing requirements, workflow-file restrictions, branch protection, and
   token expiry have no normalized handling.
7. **Observe, retry, cancel, recover:** Manual `git status`, `git ls-remote`, and
   GitHub inspection.
8. **Status:** Absent; design only. **L0.**
9. **Evidence:** `docs/DEPLOYMENT.md` says this sequence is not
   executable. Proposed broker operations exist only in
   `docs/GITHUB_INTEGRATION.md`.
10. **Leading products:** Copilot automates branch creation, commits, pushes, and
    PRs under a product identity. Jules publishes a branch or PR from its result
    page. Codex opens a PR from a reviewed cloud result.

### 11. Handle CI Failures, Reviews, Conflicts, And Follow-Ups

1. **User action:** Monitor GitHub manually, return to OpenCode, explain the
   failure or comment, verify the checkout still matches the PR head, and
   manually publish another commit.
2. **Owner:** GitHub owns checks and reviews. Fern has no poller, webhook
   receiver, correlation engine, or follow-up scheduler.
3. **Identity and credentials:** GitHub read access and publication credentials.
4. **Credential location and lifetime:** No implementation. The design proposes
   minting fresh installation tokens on wake.
5. **Durable proof:** GitHub has checks and comments. Fern has no last-seen head,
   delivery ID, review cursor, attempt number, or budget.
6. **Failure behavior:** Offline hosts cannot receive webhooks. Human edits can
   race the agent. Follow-ups can target stale heads or loop indefinitely.
7. **Observe, retry, cancel, recover:** Entirely manual through GitHub and
   OpenCode.
8. **Status:** Absent. **L0.**
9. **Evidence:** No GitHub client or operation journal exists.
   `docs/GITHUB_INTEGRATION.md` describes future polling and relay work.
10. **Leading products:** Copilot can start from failing Actions runs, respond to
    `@copilot` on PRs, and resolve merge conflicts. Codex accepts work from
    GitHub PRs and other integrations. GitHub-native products correlate against
    the durable PR head.

### 12. Sleep, Wake, Crash, Docker Restart, And Host Reboot

1. **User action:** Ordinary idle stop and wake require only an authenticated
   request. Crash or reboot failure requires logs, service shutdown, `fern down`,
   and recreation.
2. **Owner:** Fern owns protocol-aware idle stop and request wake. systemd owns
   Fern restart. Docker owns process state.
3. **Identity and credentials:** Basic auth for wake and Docker authority for
   recovery.
4. **Credential location and lifetime:** Pause intent is stored under
   `~/.fern/state` and scoped to a container ID.
5. **Durable proof:** Atomic pause intent proves an intentional Fern stop. The
   repository and named OpenCode volume survive container recreation.
6. **Failure behavior:** Fern process restart can usually reattach, but startup
   eagerly wakes paused compute. OpenCode crash is `failed`. Host shutdown of a
   running container leaves no committed pause intent and is `failed` after
   reboot.
7. **Observe, retry, cancel, recover:** `fern status --json`, logs, and manual
   `fern down` followed by `fern up`.
8. **Status:** Idle stop/wake implemented; process/host recovery incomplete.
   **L0.**
9. **Evidence:** Unit, race, and Docker fixture tests cover wake coalescing,
   admission, pause, endpoint replacement, persistence, OOM, and frozen state.
   The V2 fixture passes 13 scenarios in
   `integration/artifacts/20260816T180937Z-21024-22784/transcript.log`.
   Reboot remains broken in `docs/ARCHITECTURE.md`.
10. **Leading products:** Managed agents detach task durability from one host.
    Claude Remote Control reconnects after sleep or network loss but still
    requires its local process. Fern's safe-stop boundary is stronger than a
    generic idle timer, but does not yet provide operational recovery.

### 13. Rotate Secrets, Control Egress, And Reach Private Networks

1. **User action:** Edit `/etc/fern/fern.env`, stop Fern, run `fern down`,
   restart, and manually verify private-service reachability.
2. **Owner:** Operator, Docker networking, providers, registries, and Tailscale.
   Fern has no credential broker or network policy.
3. **Identity and credentials:** Provider key, OpenCode password, GitHub
   credential, registry token, SSH key, and private-service credentials.
4. **Credential location and lifetime:** Environment file, Fern process, and
   Docker environment. There is no expiry metadata or automatic refresh.
5. **Durable proof:** Spec fingerprint changes, but Fern records no rotation,
   credential version, lease, or scope.
6. **Failure behavior:** Rotation causes spec drift. Mid-task expiry is
   unclassified. Default Docker networking permits unrestricted egress. Fern
   has no private DNS or network readiness test.
7. **Observe, retry, cancel, recover:** Manual logs, Docker inspection, and
   network commands.
8. **Status:** Manual and unsafe. Setup/publication credentials are **L0**;
   broader egress control is **L1**.
9. **Evidence:** Container environment injection occurs in
   `internal/runtime/docker.go`; normal Docker networking is configured
   at `internal/runtime/docker.go`.
10. **Leading products:** Codex removes setup secrets before the agent phase and
    blocks agent internet by default, with domain and method allowlists. GitHub
    Apps issue short-lived repository-scoped installation tokens.

### 14. Back Up, Restore, Export, Delete, And Apply Retention

1. **User action:** Stop Fern, run `fern down`, archive the repository, Fern
   state, configuration, secrets, and Docker volume, checksum them, protect
   them, and manually reconstruct a new host.
2. **Owner:** Operator and generic host tools. Fern has no backup or restore
   command.
3. **Identity and credentials:** Root, Docker, filesystem, backup destination,
   Tailscale, provider, and GitHub credentials.
4. **Credential location and lifetime:** Backups contain service credentials and
   may contain repository secrets. Encryption and retention are external.
5. **Durable proof:** Tarballs and `SHA256SUMS`; no signed manifest,
   successful-restore record, compatibility check, or off-host acknowledgement.
6. **Failure behavior:** Partial archive, inconsistent state, missing image,
   wrong UID, orphaned volume, missing Tailscale state, expired credentials, and
   incompatible OpenCode storage require manual diagnosis.
7. **Observe, retry, cancel, recover:** Shell commands and archive inspection.
   The runbook provides no restore commands; it only advises a future restore
   test into temporary paths and a temporary Docker volume.
8. **Status:** Backup recipe documented; full restore/export/retention absent.
   **L0.**
9. **Evidence:** `docs/DEPLOYMENT.md` contains a manual, untested recipe.
   Deletion is a manual destructive sequence at `docs/DEPLOYMENT.md`.
10. **Leading products:** Managed services persist task and repository state
    independently of one host, though exportability varies. Fern's opportunity
    is a verifiable owner-controlled bundle, but no implementation exists.

## Findings By Priority

### L0: Core Outcome Cannot Complete

| Finding | Broken outcome |
| --- | --- |
| Official OpenCode UI lacks real-phone acceptance and Fern device pairing | Cannot claim supported phone start, reconnect, approve, or review |
| No GitHub App onboarding or repository selection | Cannot safely authorize or clone a private repository |
| No exact-SHA clone or setup contract | Cannot reliably prepare real private projects |
| No provider/model/quota/budget preflight | Cannot predict whether submitted work can execute |
| No durable Fern shadow operation correlated to OpenCode | Disconnect or lost response makes Fern-owned effects ambiguous |
| No notification/question/approval integration | Agent can wait indefinitely without reaching the user |
| No mobile diff, test, log, or artifact result | User cannot verify the outcome |
| No commit identity, branch broker, push, or draft PR | Main delivery outcome cannot happen |
| No CI/review reconciliation or bounded follow-up | Later declared workflow cannot happen |
| Running host reboot becomes failed | Declared reboot survival is false |
| No complete fresh-host restore | Declared host-loss recovery is false |
| No credential separation for Git/setup/registries | Private repository workflows require unsafe token exposure |
| No update/rollback appliance workflow | Server cannot be operated as a supported product |

### L1: Unsafe, Unreliable, Or Painfully Manual

| Finding | Risk |
| --- | --- |
| Shared long-lived Basic password | No user/device attribution or selective revocation |
| Provider keys visible in Docker environment | Broad credential exposure |
| Unrestricted agent egress | Repository content can exfiltrate code and credentials |
| Raw, unstructured Docker logs | Weak auditability, retention, and redaction |
| No terminal observation/takeover lease | Difficult recovery from agent mistakes |
| No request-body/connection quotas or SSE heartbeat | Ambiguous hangs and weak abuse resistance |
| Setup caches persist only accidentally in the repository | Slow and inconsistent resumes |
| No automated retention/deletion policy | Indefinite orphaned data and images |
| V2 lacks a transitive dependency integrity closure | Rebuilds are not fully reproducible |

### L2: Deferred Until L0 Is Closed

Do not prioritize L2 implementation while any L0 gap remains. Candidate later
differentiators are:

- explainable protocol-aware sleep blockers;
- whole-host wake;
- an exportable owner-controlled agent workstation;
- private wakeable artifacts and previews;
- reliable command delivery to intermittently available self-hosted machines.

### Later

- Enterprise SSO and SCIM
- Hostile multi-tenancy
- Kubernetes
- Multi-agent orchestration
- Multiplayer editing
- General workflow builder
- Cross-cloud runtime abstraction

## Smallest Complete Release

The smallest credible release supports one repository, one workspace, one user,
one OpenCode-configured provider, the official OpenCode V2 web UI, and GitHub
polling rather than public webhooks. OpenCode remains authoritative for sessions,
UI, configuration, providers, models, questions, permissions, and execution.
Fern owns lifecycle and future device auth, notifications, durable shadow
operation records, tested publication, CI reconciliation, and backup/recovery.

It must include:

Fern additions in this release scope are proposed and unimplemented unless they
are explicitly identified above as implemented.

1. **Appliance:** A signed installable release with `init`, `doctor`, systemd
   setup, safe update/rollback, and tested reboot reconciliation.
2. **Control state:** One persistent database containing device, workspace,
   lifecycle, publication, CI, artifact, and recovery shadow records correlated
   with OpenCode IDs, without replacing OpenCode session state.
3. **Browser surface:** Pass the released OpenCode server's embedded official UI
   through Fern unchanged at `/`; reserve minimal `/fern/*` controls. Device
   pairing, cookie sessions, and notifications are proposed. A narrow phone
   companion is only a fallback after the official UI fails real-phone
   acceptance, not the release default.
4. **GitHub:** Private GitHub App onboarding for one repository, exact-SHA
   host-side clone, and short-lived host-only installation tokens.
5. **Environment:** One versioned setup/resume hook, setup-only secrets,
   persistent dependency caches, submodule/LFS handling, and explicit setup
   failure state.
6. **Execution:** OpenCode-owned sessions that survive browser disconnect as
   supported upstream, plus idempotent Fern shadow operations for lifecycle and
   external side effects. Provider/model configuration remains in OpenCode;
   Fern may impose runtime/cost lifecycle limits.
7. **Delivery:** Deterministic commit identity, one Fern-owned branch,
   exact-commit host-brokered push, and one tested draft PR.
8. **Continuation:** Poll GitHub for the current PR head, checks, review
   comments, conflicts, and revocation, with bounded follow-up attempts.
9. **Recovery:** Automated encrypted backup, manifest verification, fresh-host
   restore rehearsal, retention, export, and safe deletion.
10. **Acceptance test:** From the official OpenCode UI on a real phone, authorize a private
    fixture repository, submit work, disconnect, answer one approval, inspect a
    test result and diff, receive a draft PR, process one failing check or review
    comment, pause, reboot, and restore on another host.

This closes the complete user outcome without adding multi-workspace
orchestration, a general workflow engine, hosted webhook infrastructure,
Kubernetes, or multi-agent features.
