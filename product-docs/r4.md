# Fern R4 Outside-In Adversarial Product Audit

> Post-audit update (2026-08-16): Fern now has process-local one-time phone
> pairing, `/fern/*` landing/readiness routes, `fern init`, `fern doctor
> --phone`, and an explicit host-only draft-PR publication prototype. Historical
> findings below describe the audited snapshot; durable device identity,
> GitHub App onboarding, notifications, and real-phone acceptance remain open.

Audit date and external-source access date: **2026-08-16**

Target outcome:

> From my phone, connect a private repository, ask an agent to make a change,
> let it work while I disconnect, answer any questions or permissions, inspect
> the result, and receive a tested draft pull request. Later, handle CI failures
> or review feedback, survive sleep and reboot, and restore the workspace after
> host loss.

## 1. Executive verdict

Fern cannot complete any end-to-end instance of the outcome. It is a careful
single-workspace OpenCode container lifecycle proxy, not a remote coding-agent
product. Its executable product ends at authenticated HTTP admission, Docker
wake, protocol-aware idle observation, conservative stop classification, a
writable host directory, and a persistent OpenCode volume. It owns no user,
device, repository, task, attempt, approval, result, tested commit, publication,
PR, CI event, backup, or restore record (`cmd/fern/main.go`,
`internal/registry/intent.go`, `internal/runtime/runtime.go`).

Amp is the end-to-end benchmark: Orb threads can start remotely, continue after
client disconnect, be used from mobile web, expose files/terminal/portals, and
push changes. But PR creation is guidance-driven, permissions are permissive by
default, and Orb worker recovery, replay, notification delivery, conflict
control, and per-task cost ceilings are undocumented. T3 Code is the stronger
open interaction benchmark: native mobile/web clients, durable event-sourced
threads, provider adapters, reconnect, terminal, worktrees, diffs, and Git
surfaces are shipped. It is also alpha-quality: volatile provider ingestion,
provider-state divergence, single-writer defects, process loss, and unstable
private protocols make it unsuitable as Fern's durability authority.

**Recommendation: EXPOSE OPENCODE; NARROW FERN.** The released OpenCode V2 server
embeds and serves its official web UI at its origin root. Fern should expose that
UI unchanged through its wake-aware authenticated reverse proxy, with only
minimal Fern control routes reserved under `/fern/*`. OpenCode remains the
user-facing authority for sessions, UI, configuration, providers, models,
permissions/forms, tools, worktrees, VCS inspection, and conversation state.
Fern owns lifecycle and, when implemented, device authentication, notifications,
durable shadow operation records, tested publication, CI reconciliation, and
backup/recovery. Do not build or maintain a second coding UI; T3 remains
historical competitive evidence only. A narrow phone companion is only a fallback
if the unchanged official UI fails real-phone acceptance.

No L2 work is justified while the L0 register in section 23 is non-empty.

## 2. Audit scope, method, and evidence actually collected

### Method

1. Read every file in `product-docs/` before inspecting implementation.
2. Treated agreement among `r1`, `r2`, and `r3` as a claim, not evidence.
3. Inspected all tracked first-party Go code, tests, scripts, Dockerfiles,
   deployment examples, CI, documentation, ignored-file rules, local artifacts,
   and recent Git history. The ignored `opencode/` checkout was not counted as
   Fern functionality.
4. Ran feasible non-destructive tests from the current checkout.
5. Researched current official Amp and competitor documentation and current T3
   source, releases, issues, license, dependency model, and CLI behavior.
6. Classified every assertion as executable, documented, delegated with or
   without integration, assumed, or unsupported.

## 5. Corrections to `r1.md`

- Historical findings about the removed protocol path and auto-detection are superseded. The
  supported architecture is V2-only and must have one unambiguous authentication
  path before wake.
- A compatible mobile HTTP client is not protocol-impossible; it is unnamed,
  untested, unsupported, and lacks product state.
- Claims that specific OpenCode questions/tables are process-local exceed Fern
  evidence. The proven fact is that Fern persists none of them.
- "Stops only when safe" must be qualified by sequential V2 snapshots and the
  check-to-stop race (`internal/workspace/manager.go`).

## 6. Corrections to `r2.md`

- Installation/update is L0 for the declared outcome, not L1.
- Provider/model validity and a hard budget are L0, not wholly L1.
- The quick-start authentication finding is incorrect: current `README.md`
  diagnostics use `curl --user` with `OPENCODE_PASSWORD`.
- "No dependency caches" should read "no Fern-managed/versioned cache
  contract"; repository-local caches may persist accidentally.
- CI definition is coverage intent, not a passed current CI run.
- The report missed the implicit plaintext attach path, eager startup wake,
  corrupt-intent cleanup failure, and custom-image runtime policy.

## 7. Corrections to `r3.md`

- Lifecycle artifacts are ignored local files, not checked-in evidence
  (`integration/.gitignore:1`).
- "Pre-existing OpenCode workspace" should be "pre-existing host directory";
  Fern creates the container and volume.
- Raw logs are L1, but immutable diff/test evidence is L0.
- Provider volatility claims must be labeled upstream/documentation evidence.
- "SSE-only reconnect does not wake" is correct but is a product behavior gap,
  not proof a future task client must wake via SSE.

Amp's operational assumptions are Amp account availability, GCP/Amp Server,
e2b Orbs, model providers, Git host access, repository-authored hooks, and
trusted plugins. Its lock-in is thread storage, Orb runtime, portals, webhooks,
and billing. Its privacy advantage over local agents is limited: partial code
and threads traverse/store in Amp and Orb code reaches e2b. Fern can be better
only if it makes self-hosting operationally credible and state export/restore
verifiable; merely running Docker locally is not enough.

## 10. Historical T3 Code benchmark

Audited `pingdotgg/t3code` `main` at
`fee10def1afb63cecd9a626aeba2bb063828cf22`; stable `v0.0.33` (2026-08-10).
The project was reviewed as a historical interaction and failure-mode benchmark.
It is not an architecture option for Fern; no T3 server, client, package, or
fork belongs in the release path.

### Shipped

- Web, Electron, iOS, Android, and `npx t3@latest`; responsive web plus native
  conversation, terminal, review, files, Git and settings routes
  ([README](https://github.com/pingdotgg/t3code/blob/fee10def1afb63cecd9a626aeba2bb063828cf22/README.md)).
- Server-owned typed RPC/WebSocket boundary; clients do not directly execute
  provider, Git, PTY, or filesystem operations
  ([overview](https://github.com/pingdotgg/t3code/blob/fee10def1afb63cecd9a626aeba2bb063828cf22/docs/internals/overview.md)).
- SQLite event log/projections and transactional command receipts provide local
  command idempotency. Provider/thread binding and resume cursor persist.
- Built-in adapters for Codex, Claude, Cursor, Grok Build, and OpenCode; users
  must separately install/authenticate those CLIs. This is inherited behavior,
  not T3 implementation.
- Direct pairing, LAN/Tailscale, SSH, headless service, and hosted T3 Connect.
- PTYs, replayable history, Git/worktrees/checkpoint refs, diffs/revert,
  GitHub/GitLab/Bitbucket/Azure hosting workflows.

### Failure reality

- Provider events traverse an unbounded in-memory queue before durable
  projection; issue
  [#6560](https://github.com/pingdotgg/t3code/issues/6560) describes memory/loss
  and stuck turns.
- Provider-native context can diverge from restored files/thread projection
  ([#6127](https://github.com/pingdotgg/t3code/issues/6127)); OpenCode approvals
  can survive teardown ([#7113](https://github.com/pingdotgg/t3code/issues/7113)).
- PTY history persists but the process is memory-owned and cannot be reattached
  after server restart.
- Desktop and background service can open the same T3 home/database
  ([#6097](https://github.com/pingdotgg/t3code/issues/6097)), violating
  single-writer authority.
- Reconnect has infinite transient retry and offline cache, but foreground probe
  failure can tear down a healthy lease
  ([#7231](https://github.com/pingdotgg/t3code/issues/7231)).
- Native/mobile features are real but current issues include Android question
  layout and iOS relay/notification failures (#6347, #7170).

### Dependency and reuse risk

Private workspace packages, beta Effect APIs, patched dependencies, native
Expo/Electron/node-pty stacks, and an unstable shared-source RPC schema make
library embedding risky. `@t3tools/contracts` and client runtime are private,
not semver-stable packages. A current dependency audit reported production-path
advisories; reachability was not independently established. T3 Connect adds
Clerk, Cloudflare, PlanetScale, Vercel, Axiom and APNS assumptions. Release
artifacts may be unsigned when signing credentials are absent.

This evidence supports only the rejection decision: do not use T3 code or runtime
components. The official OpenCode V2 web UI is the sole default browser surface.

## 14. Newly discovered gaps, labeled `NEW`

The canonical finding register below supplies every required finding field.

### `NEW-RUNTIME-01`: Non-atomic quiescence-to-stop boundary

- **Severity/priority/confidence:** Critical, L0, high.
- **Why missed:** Prior reports noted sequential V2 reads but accepted the final
  barrier as effectively safe; they did not carry the race through Docker stop.
- **Impact/scenario:** OpenCode creates internal work after its surface is read
  but before `ContainerStop`; Fern records a safe pause while killing live work.
- **Missing authority/state:** An OpenCode-issued quiescence lease/epoch covering
  all work surfaces through stop.
- **Refs/evidence:** `watch.AllSessionsIdle` at `internal/watch/status.go:19-29`,
  `internal/workspace/manager.go`, `docs/ARCHITECTURE.md`;
  current tests simulate stable snapshots only.
- **Owner now/future; recovery:** Fern/OpenCode; runtime adapter plus OpenCode;
  user can only inspect and retry from durable work.
- **Gate/acceptance:** Narrow safety claim or add upstream quiescence token;
  inject activity after each final read and prove stop refuses it (`AT-30`).

### `NEW-RUNTIME-02`: Startup wakes safely paused compute

- **Severity/priority/confidence:** High, L0, high.
- **Why missed:** Mentioned as a detail, not recognized as defeating sleep/cost
  behavior on every service restart or boot.
- **Scenario/state:** `fern up` calls `EnsureRunning`; committed paused state is
  immediately resumed without a user command. Required durable state is desired
  run mode plus pending wake ID.
- **Refs/evidence:** `cmd/fern/up.go`,
  `internal/runtime/docker.go`.
- **Owner/recovery/gate/test:** Fern runtime; user currently stops it again;
  startup must serve control plane while preserving paused compute; reboot a
  paused host and prove zero container start until durable task/wake (`AT-34`).

### `NEW-RUNTIME-03`: Stopping Fern leaves uncontrolled credentialed compute

- **Severity/priority/confidence:** High, L1, high.
- **Why missed:** Prior reports described reattach benefit but not controller
  absence as a safety and cost condition.
- **Scenario/state:** `systemctl stop fern` leaves OpenCode running with secrets,
  no watcher or idle controller. Need durable maintenance mode and coordinated
  quiesce outcome.
- **Refs/evidence:** `cmd/fern/up.go`,
  `deploy/systemd/fern.service`.
- **Owner/recovery/gate/test:** Fern/appliance; operator manually `down`; service

- **Severity/priority/confidence:** Critical, L1, high.
- **Why missed:** Reports trusted shipped image and overlooked configurable

## 16. Security and credential-custody review

Current secrets enter `/etc/fern/fern.env`, the Fern process and Docker
configuration (`cmd/fern/helpers.go`, `internal/runtime/docker.go`).
Repository code, hooks, tools, tests, dependencies, root and Docker-capable users
can read them. The container has default egress (`internal/runtime/docker.go`)
and no DNS, proxy, metadata, LAN, tailnet, private-service, destination, or audit
policy. Logs are raw Docker streams with no redaction contract
(`internal/runtime/docker.go`). Backups explicitly contain credentials
(`docs/DEPLOYMENT.md`).

Minimum boundary: provider credential remains in a host-side inference proxy or
is a task-scoped lease; setup/registry secrets exist only in setup subprocesses;
GitHub App key and installation tokens never enter workspace; signing is
unsupported in release one unless host-held signing is implemented; artifact
links are short-lived device-authorized grants. Deny cloud metadata and host/LAN
by default; allow provider, selected GitHub, package registries and explicitly
declared private endpoints; log destination metadata without credentials.

Revocation must increment a credential version, cancel leases, invalidate
caches populated by that credential where necessary, and make resumed/restored
attempts preflight again. Redaction must cover app logs, Docker logs, test logs,
artifacts, screenshots, crash dumps and support bundles; "application logs are
redacted" alone is insufficient.

## 17. Durability, idempotency, and recovery state-machine review

Sections 17 through 31 describe proposed release behavior. Every capability is
unimplemented unless it is explicitly labeled current or implemented.

Proposed Fern-owned SQLite entities (none are implemented today):

`appliance(id, epoch, version)`, `device`, `repository(immutable_id,
installation_id)`, `workspace(base_sha, image_digest, setup_version)`,
`shadow_operation(idempotency_key, opencode_session_id, opencode_message_id,
kind, state)`, `attempt(sequence, execution_version, state, deadline, cost)`,
`notification(opencode_event_id, delivery_state)`,
`tool_effect`, `test_run(tree_oid, environment_digest)`, `artifact(digest)`,
`publication(operation_id, commit_oid, remote_sha, pr_number)`,
`github_cursor(pr_head, check/review_cursor)`, `backup(manifest_digest, epoch)`.

Fern operation states may be `queued -> delivering -> applied -> running ->
waiting` and then `completed|failed|cancel_requested|canceled|expired|uncertain`.
They shadow Fern-owned lifecycle or external side effects; they do not replace
OpenCode session/message state. Delivery is at-least-once and deduplicated by a
stable operation/message correlation ID. Never claim exactly once across
provider/tools/GitHub. Cancellation fences Fern publication effects, requests
upstream stop through supported OpenCode APIs, and records acknowledgment
separately. Recovery reconciles Fern records, OpenCode session state, process
state, worktree/Git OIDs, and GitHub remote state before Fern resumes effects.

OpenCode remains authoritative for user-facing sessions, UI, configuration,
providers/models, conversation, permissions/forms, and live tool protocol. Fern
owns lifecycle and proposed device authentication, notification delivery,
durable shadow operations, result provenance for publication, publication, CI
reconciliation, and recovery. Git object IDs are authoritative for content;
GitHub numeric repository/installation/PR IDs and remote refs are authoritative
remotely; Fern stores expected/cursor state and reconciles.

## 18. Git and GitHub publication review

Current status is unsupported; `docs/GITHUB_INTEGRATION.md` is explicitly a
proposal. Release-one publication must occur in a host broker using an appliance
GitHub App, immutable repository ID, selected installation, fresh repository-
scoped token, hooks disabled, sanitized Git config, exact base SHA, and a Fern
branch. The container receives no GitHub token or arbitrary API proxy.

Reject replace refs, grafts, alternates outside workspace, bare/non-Git repos,
symlink escapes, object corruption, unexpected object format, dirty preexisting
state, nested repos, submodules/LFS, remote mismatch, force-push, tags/notes,
default-branch push, workflow changes, protected/rules-incompatible branches,
and human changes to the Fern branch. Release one supports SHA-1 Git only;
SHA-256 must fail preflight until GitHub and all tooling are proven compatible.

Commit identity is fixed bot author/committer, UTC timestamp policy declared,
unsigned commits, no arbitrary trailers, deterministic branch
`fern/<task-id>`. Push exact attested commit with expected remote old SHA. On
ambiguity query remote. PR operation stores head/base/commit/number and finds an
existing exact PR before creation. Human edit, push, closure, merge or deletion
becomes a visible terminal/conflict state; never overwrite it automatically.

## 19. Environment, dependency, and cache review

Release one supports one repository-owned executable setup script with a pinned
setup version/hash, 20-minute timeout, 8 GiB disk quota, cancellable process
group, complete redacted log, and explicit success marker bound to base SHA,
lockfiles, image digest and secret versions. Resume hook is limited to five
minutes and separately logged. Setup runs before agent credentials are exposed.

Support public npm/pnpm, PyPI/pip and Go modules only, plus one configured HTTPS
private npm registry through a scoped setup-only token. Do not promise private
PyPI/Cargo/Maven/container registries, SSH dependencies, private Go proxies,
recursive private submodules or private networks in release one. Persistent
caches need quota, content/setup key, provenance, reset and corruption fallback;
they must not persist credential files. Disk-full injection must leave task and
cache state recoverable.

## 20. Runtime, reboot, and host-loss review

Implemented strengths: local-Docker restriction, ownership labels, loopback
backend, CPU/memory/PID bounds, process-local wake coalescing, request/pause
exclusion, atomically written pause intent, conservative failure classification,
and real-Docker simulator coverage.

Release behavior must separate daemon state from compute state. Daemon startup
must not wake paused compute. Planned host shutdown writes a shutdown intent,
quiesces or marks the active attempt interrupted, and stops compute. Unplanned
running reboot becomes `recovery_required`, not a dead-end `failed`; it starts a
new bounded attempt only after reconciling files/OpenCode/task state. OpenCode
crash, tool crash, OOM, disk full, corrupt SQLite, clock change, Docker ambiguous
response and silent watcher all become distinct visible states. Mid-turn replay
is not promised; completed durable tool/Git effects are reconciled and the agent
is asked to continue in a new attempt.

Whole-host wake is excluded: a powered-off host cannot receive its own wake
command. The first release requires the host powered on; container scale-to-zero
only.

## 21. Backup, restore, export, deletion, and retention review

The current quiet tar recipe is local, manual, unencrypted, unsigned, incomplete
and untested (`docs/DEPLOYMENT.md`). It omits an executable immutable
release/image identity and useful restoration semantics for old container-bound
pause intent.

Release backup must quiesce publication, checkpoint SQLite, record Git fsck and
all refs/worktree, OpenCode supported state, artifacts, config without active
plaintext leases, image/binary digests, schema versions, credential metadata,
and appliance epoch in a signed/checksummed encrypted manifest. Replicate
off-host and record acknowledgement. Encryption key must not exist only on the
lost host. Restore order: verify provenance, install exact compatible binary and
image, create new appliance epoch, restore DB/Git/artifacts/OpenCode, migrate,
invalidate old host, require provider/GitHub/Tailscale reauthorization or
revalidation, reconcile GitHub, then enable execution.

Retention: task/log/artifact 30 days by default; backups 7 daily + 4 weekly;
worktree until workspace deletion; GitHub/provider copies follow their systems.
Deletion produces an inventory/receipt for local DB, files, volumes, images,
logs and backups, and states that GitHub commits/PRs, provider/Amp/T3 copies and
remote backups require separate deletion. Secure erasure on SSD/object stores is
not guaranteed; cryptographic key destruction plus provider deletion is the
honest contract.

## 22. Supply-chain review

Current binaries have local checksums but no distribution, signature,
attestation or SBOM (`scripts/build-release.sh`). Version is caller-chosen
and not tied to a signed tag (`scripts/build-release.sh`). CI actions use
mutable major tags (`.github/workflows/ci.yml`). The consolidated V2 image
has digest-pinned bases but unversioned apt packages and no transitive
lock/integrity closure; npm scripts execute as root
(`images/opencode/Dockerfile`).

Release gate: signed tag, reproducible or independently rebuilt binaries,
digest-pinned image, SBOMs, SLSA-style provenance, cosign/signature verification,
commit-pinned Actions, dependency/vulnerability/secret scans, published update
channel, compatibility manifest, backup-before-update, staged health check and
automatic rollback. A compromised update requires revocation metadata,
quarantine, credential rotation and restore from a known-good manifest.

## 27. Assumptions requiring explicit product decisions

1. Host remains powered on; no whole-host wake.
2. One user, host, GitHub installation, repository, workspace, provider/model
   policy and active task.
3. OpenCode may lose in-flight work; Fern restarts an attempt, not a process.
4. Unsigned deterministic bot commits are acceptable for supported repos.
5. Repository and dependencies are trusted but not trusted with GitHub/provider
   master credentials.
6. Polling GitHub every 60 seconds is sufficient; no public webhook service.
7. The official OpenCode UI is the default phone/browser surface. A Fern cookie
   gateway, device pairing, and notifications are proposed and unimplemented. A
   narrow companion is considered only after failed real-phone acceptance.
8. Setup/private dependency support is deliberately narrow.
9. Self-host value justifies an Ubuntu/Docker/Tailscale operational contract.
10. The released OpenCode V2 server's embedded UI can be proxied unchanged and
    version-pinned without coupling Fern to OpenCode's private database.

## 28. Supported first-release repository profile

- GitHub.com private repository, one appliance GitHub App installation and one
  immutable repository ID; SHA-1 object format.
- Maximum clone 2 GiB, checkout 5 GiB, 100,000 files; one worktree; no monorepo
  special semantics beyond one root setup/test contract.
- No submodules, Git LFS, nested repositories, alternates, grafts, replace refs,
  sparse/partial clone, bare repository, symlink escape or existing dirty state.
- Ubuntu 24.04 LTS amd64 only; local rootful Docker; 4 CPU, 16 GiB RAM, 50 GiB
  free disk; host stays on; private HTTPS via supported Tailscale Serve.
- Node/pnpm/npm, Python/pip and Go; lockfiles required where applicable. One
  HTTPS private npm registry supported with setup-only token. Public package
  Internet plus explicit provider/GitHub endpoints.
- Executable `.fern/setup` and `.fern/test` contracts, pinned by base SHA;
  setup <=20 minutes, task <=60 minutes, one follow-up <=30 minutes.
- One provider and model allowlist; hard dollar/token/runtime budget. No failover.
- Fern-owned branch; no human push while task active; no workflow-file changes;
  repository rules must permit unsigned Fern bot commits and draft PRs.
- One active task, maximum three attempts including one CI/review follow-up.
- Preflight rejects unsupported features before clone/setup/provider spend and
  gives exact reason/remediation.

## 29. Unsupported first-release repository conditions

GitLab/Bitbucket/GHES, forks, multiple repos, >limits, SHA-256 Git, submodules,
LFS, private PyPI/Cargo/Maven/Go/container registries, SSH dependencies, private
network dependencies, signed-commit-required rules, required custom author,
workflow changes, generated credentials in repo, custom Docker daemon, rootless
Docker, non-Ubuntu hosts, ARM, Kubernetes, untrusted multi-user repos, binary
artifacts requiring previews, tasks over budget/duration, and concurrent human
writes. Detection is a hard preflight failure, not best effort.

## 32. Smallest release completing the entire outcome

### Included

- One signed Ubuntu 24.04 amd64 appliance installer with `init`, `doctor`,
  digest-pinned image, migrations, update/rollback and systemd/Tailscale setup.
- The released OpenCode V2 server's official embedded web UI, exposed unchanged
  at `/` through Fern's wake-aware authenticated reverse proxy. Minimal
  Fern-specific controls live only under `/fern/*`.
- Proposed one-time pairing, cookie gateway, revocable device session, and
  notifications. These are release requirements, not current implementation.
- One Fern SQLite shadow-operation state machine for lifecycle, tested
  publication, CI reconciliation, and recovery, correlated to OpenCode IDs.
- One private GitHub.com repository through an appliance App, exact-SHA host
  clone, deterministic unsigned bot commit, exact push and exactly one draft PR.
- One pinned OpenCode V2 service integration. OpenCode owns provider/model
  configuration; Fern may enforce a hard runtime/token/cost lifecycle cap and
  keep provider credentials outside
  repository-controlled processes where feasible.
- One setup/test contract and private npm setup lease; bounded cache.
- Poll GitHub every minute for exact-head CI/review/conflict state and permit one
  bounded user-approved follow-up.
- Reboot/Docker/process reconciliation, encrypted off-host backup, appliance
  fencing, and tested fresh-host restore.

### Excluded

Custom coding UIs, T3 implementation components, native apps,
terminal takeover, previews/video, multiple users/repos/tasks,
webhooks, whole-host wake, provider failover, submodules/LFS, commit signing,
arbitrary registries/networks, multi-agent, Kubernetes and enterprise identity.

### Match/adopt/integrate boundaries

- **Match Amp:** remote start, durable thread/task, continue disconnected,
  mobile follow-up, setup logs, progress/diff, bounded terminal evidence,
  branch handoff, reconnect and visible cost.
- **Do not match Amp:** managed Orbs, modes/model routing, plugins/schedules,
  multiplayer, portals, Amp-hosted Git or permissive default tools.
- **T3 boundary:** Historical competitive evidence only. Do not integrate,
  vendor, or fork any T3 component.
- **OpenCode UI:** Serve the official embedded UI unchanged at `/`; maintain no
  custom upstream UI code.
- **OpenCode responsibilities:** model loop, provider/model configuration, live
  sessions, permissions/forms, tool and shell/PTY execution, worktrees, VCS
  inspection and conversation UI. Fern records correlation and outcome, not
  reasoning, and never treats the OpenCode database as its task journal.
- **Fern-owned durable state:** future device grants and notifications; repo/base,
  lifecycle and external-operation shadows; setup/test evidence; publication,
  GitHub cursor, appliance epoch, and backup/restore. OpenCode remains session,
  permission, UI, config, and provider authority.
- **External authority:** Git object IDs for content; GitHub IDs/refs/PR/checks/
  reviews; provider for accepted usage/billing; Tailscale for network membership.

### Release gates

All 42 acceptance rows pass on disposable hosts; every L0 finding is closed or
the supported profile rejects it before side effects; no credential appears in
workspace env/log/artifact; tested commit equals PR head; restore split-brain
test passes; and one non-developer completes install-to-restored-PR from docs.

### Product thesis

Fern can be the smallest self-hosted control plane that gives one developer an
Amp-quality remote outcome on a machine they own, while making command delivery,
tested Git publication, failure state and fresh-host restoration more explicit
and verifiable than managed agents. Its differentiation is not local Docker,
hibernation, chat, or model choice; it is owner-controlled execution plus a
falsifiable durable state and recovery contract.

### Argument against the thesis

The target user may prefer Amp, Cursor, Copilot, Codex, Claude web, T3 plus a
background service, Coder, or OpenHands because they already solve most visible
workflow pain without asking the user to administer Ubuntu, Docker, Tailscale,
GitHub Apps, secrets, backups and restore drills. Fern's claimed advantage may
require building an appliance, workflow engine, credential broker, GitHub
integrator, mobile client and recovery system merely to reach table stakes; the
operational and security burden can erase the privacy/cost value, while OpenCode
and managed-agent product surfaces continue to improve independently.

### Final recommendation

**EXPOSE OPENCODE AND NARROW FERN, with explicit pivot/stop gates.** Treat the
pinned released OpenCode V2 service and its embedded official web UI as the
primary product primitive. Expose it unchanged at `/`; reserve `/fern/*` for
minimal Fern controls. The proposed, unimplemented Fern scope is lifecycle,
device auth and notifications, durable shadow operations, GitHub publication,
CI reconciliation, appliance, and recovery boundaries. Keep T3 as historical
evidence only and leave the OpenCode UI unchanged.
Do not fund L2
differentiation until every L0 acceptance test passes. If OpenCode cannot supply
the required public hooks, first propose or build those hooks upstream; switch
engines or pivot to Coder/Daytona only if that bounded effort fails.
