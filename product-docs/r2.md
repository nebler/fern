# Fern End-to-End Product Audit

## Verdict

Fern cannot currently complete the target user outcome:

> From my phone, connect a private repository, ask an agent to make a change,
> let it work while I disconnect, answer any questions or permissions, inspect
> the result, and receive a tested draft pull request. Later, handle CI failures
> or review feedback, survive sleep and reboot, and restore the workspace after
> host loss.

Fern implements a careful, well-tested lifecycle wrapper around one existing
host directory and one OpenCode container. It does not implement the surrounding
remote coding-agent product: validated phone access, durable Fern shadow
operations, repository authorization, environment setup, Git publication, CI
continuation, reboot recovery, or fresh-host restore.

The repository states this accurately in `docs/REMOTE_PRODUCT.md` and
`README.md`.

The V2-only architecture direction is not implementation evidence. Device
pairing, a browser cookie gateway, notifications, tested publication,
attach-existing-service mode, and real-phone validation are proposed or
unperformed, not implemented.

Status terms used below:

- **Implemented:** Fern owns and executes the operation.
- **Documented:** A manual procedure exists, but Fern does not execute it.
- **Delegated:** Another component may perform it, without a Fern integration.
- **Assumed:** The outcome depends on behavior that Fern neither verifies nor
  controls.
- **Unsupported:** The end-to-end operation cannot currently be completed as a
  Fern product workflow.

- Host reboot recovery

## Findings By Priority

### L0: Release Blockers

#### L0-1: Official Browser Surface Is Not Yet A Validated Phone Product

The released OpenCode V2 server embeds and serves its official web UI at its
origin root. The product architecture is to expose that UI unchanged through
Fern's wake-aware authenticated reverse proxy, not to build a second coding UI.
Fern-specific browser controls should be limited to
reserved `/fern/*` routes. Real-phone validation has not been performed.

There is no Fern pairing, device registration, revocation, cookie session, push
notification, or offline lifecycle/publication status. OpenCode's own session,
permission, and result UI remains authoritative and must be mobile-tested.

References:

- `docs/REMOTE_PRODUCT.md`
- `internal/proxy/proxy.go`
- `docs/DEPLOYMENT.md`

#### L0-2: A Proxied Request Has No Durable Fern Shadow Operation

OpenCode owns the session, but Fern has no correlated shadow-operation ID,
idempotency key for Fern-owned effects, attempt record, cancellation intent,
publication result, retry policy, or delivered/applied distinction.

If a request or response is lost, Fern cannot establish whether the instruction
was never received, received but not applied, running, completed, canceled, or
applied twice after retry. HTTP cancellation only cancels the caller's wait. It
does not prove OpenCode or the provider stopped.

References:

- `internal/workspace/manager.go`
- `docs/REMOTE_PRODUCT.md`
- `docs/REMOTE_PRODUCT.md`

#### L0-3: No Repository Authorization Or Checkout Integration

The operator manually clones a repository before Fern starts. Fern only checks
that `workspace.repo` is a directory, not that it is a Git repository or the
repository the user authorized.

There is no GitHub App, repository picker, immutable repository ID, base SHA,
clone credential, installation revocation handling, or origin reconciliation.

References:

- `docs/DEPLOYMENT.md`
- `internal/config/config.go:396-402` (`config.ValidateWorkspace`)
- `docs/GITHUB_INTEGRATION.md`

#### L0-4: No Branch, Commit, Push, Or Draft PR Integration

Fern does not configure:

- Commit author or committer identity
- Commit signing
- Branch namespace
- Base commit
- Credential helper
- Push authorization
- Draft PR creation
- Ambiguous push reconciliation
- Protection against default-branch or force pushes

The GitHub broker is a proposal only.

References:

- `docs/DEPLOYMENT.md`
- `docs/GITHUB_INTEGRATION.md`

#### L0-5: No Supported Project Setup Boundary

The container mounts only the repository and OpenCode state. There are no
versioned setup/resume hooks, setup logs, timeouts, setup failure states, or
dependency caches.

There is no integrated support for:

- Private npm, PyPI, Cargo, Maven, Go, or container registries
- Git submodules
- Git LFS
- Nested repository authorization
- Cache invalidation or quotas

A repository process can run arbitrary setup commands, but that is delegation
without onboarding, credential isolation, or evidence.

References:

- `internal/runtime/docker.go`
- `docs/REMOTE_PRODUCT.md`
- `docs/REMOTE_PRODUCT.md`

#### L0-6: Questions And Permissions Are Not A Product Workflow

V2 permissions and forms correctly block idle stopping. Fern cannot notify the
user, display the request, persist it, answer it, audit the answer, expire it, or
recover it after OpenCode exits.

References:

- `internal/watch/status.go:19-29` (`watch.AllSessionsIdle`)
- `internal/watch/status_test.go`
- `docs/REMOTE_PRODUCT.md`

#### L0-7: No Mobile Result Or Intervention Surface

Fern exposes container logs and a raw event debugger to the host CLI. It does
not expose authenticated mobile views for:

- Diff and changed files
- Test summary and full test logs
- Generated artifacts
- Screenshots or videos
- Application previews
- Terminal observation or takeover

References:

- `cmd/fern/commands.go`
- `docs/REMOTE_PRODUCT.md`
- `docs/REMOTE_PRODUCT.md`

#### L0-8: No CI, Review, Conflict, Or Follow-Up Loop

Fern has no GitHub webhook receiver, polling loop, event journal, PR-head
correlation, review-comment ingestion, conflict policy, retry limit, or
follow-up attempt model.

A sleeping private host also cannot receive GitHub webhooks. The proposed public
relay is not implemented.

References:

- `docs/GITHUB_INTEGRATION.md`
- `docs/REMOTE_PRODUCT.md`

#### L0-9: A Running Workspace Does Not Survive Host Reboot Automatically

If Docker stops a running container during host shutdown, there is no committed
Fern pause intent. On reboot, Fern classifies the container as failed and
refuses automatic recovery. The operator must investigate and recreate it.

A Fern process restart is safer: if Docker and OpenCode remain alive, Fern can
reattach.

References:

- `docs/DEPLOYMENT.md`
- `internal/runtime/docker.go`
- `docs/ARCHITECTURE.md`

#### L0-10: Fresh-Host Restore Is Not Implemented

The runbook provides manual archive commands and advises a future restore test
into temporary paths and a temporary Docker volume, but provides no extraction
or restore procedure. It does not restore and validate the complete system on a
fresh host:

- Fern version and image
- Repository and uncommitted state
- OpenCode data
- Configuration and secrets
- GitHub installation state
- Task and PR state
- Systemd and Tailscale exposure
- Functional provider access

References:

- `docs/DEPLOYMENT.md`
- `docs/REMOTE_PRODUCT.md`
- `README.md`

### L1: Reliability, Safety, And Manual-Operation Gaps

#### L1-1: Installation And Upgrades Are An Operator Runbook

Installation requires manually installing Docker, Go, Tailscale, accounts,
directories, source, binaries, images, secrets, systemd, and Tailscale Serve.
The repository explicitly says the complete procedure has not been run.

There is no installer, `init`, `doctor`, updater, migration, rollback, package
repository, signed release, or published image workflow.

References:

- `docs/DEPLOYMENT.md`
- `docs/DEPLOYMENT.md`
- `cmd/fern/cli.go`

#### L1-2: Provider Onboarding, Models, Quotas, And Budgets Are Not Fern Operations

Provider keys are manually placed in host environment files and forwarded into
Docker. Fern does not authenticate through OAuth, test provider access before a
task, list or validate models, surface quota failures, estimate or cap cost,
rotate credentials, or stop work at a budget boundary.

Model configuration and provider errors are delegated to OpenCode without a
Fern integration.

References:

- `cmd/fern/helpers.go`
- `internal/runtime/docker.go`
- `docs/REMOTE_PRODUCT.md`

#### L1-3: Shared Static Basic Authentication

Fern has one non-expiring shared password. Tailscale enrollment is an external
outer boundary, not Fern device pairing.

There is no per-device principal, short-lived Fern session, access audit,
revocation list, rate limit, or compromised-phone flow. Authentication before
wake itself is implemented and well tested.

References:

- `internal/proxy/auth.go`
- `internal/proxy/auth_test.go`
- `docs/REMOTE_PRODUCT.md`

#### L1-4: Secrets Are Exposed To Repository Code And Docker Administrators

Provider keys and arbitrary `workspace.env` values enter container environment
variables. Repository-controlled processes can read and exfiltrate them. Root
and Docker-group users can inspect them.

There is no separation between provider, setup, registry, Git publication,
preview, or signing credentials.

References:

- `cmd/fern/helpers.go`
- `internal/runtime/docker.go`
- `docs/DEPLOYMENT.md`
- `docs/DEPLOYMENT.md`

#### L1-5: Unrestricted Egress

The workspace receives default Docker networking. There is no allowlist, DNS
policy, destination audit, provider/package/Git separation, or denial test.
Private-network access is accidental host routing, not an integrated,
observable capability.

Reference: `internal/runtime/docker.go`.

#### L1-6: Unsafe Repository-Path Contract

Any existing directory can be mounted read/write. Fern does not reject `/`,
sensitive host paths, symlink escapes, non-Git directories, untrusted ownership,
or an unexpected origin.

References:

- `internal/config/config.go:396-402` (`config.ValidateWorkspace`)
- `internal/runtime/docker.go`

#### L1-7: Signing And Supply-Chain Provenance Are Absent

Unsigned commits might be acceptable for a first supported profile, but Fern
does not declare or enforce a policy. Installation artifacts have checksums but
no signatures, attestations, SBOM, or published provenance.

The V2 image pins the top-level npm package but not a transitive lockfile.

References:

- `scripts/build-release.sh`
- `images/opencode/Dockerfile`
- `docs/ARCHITECTURE.md`

#### L1-8: Backup, Deletion, Export, And Retention Remain Manual

Backups are unscheduled and unencrypted by Fern. There is no rotation, retention
policy, portable export bundle, restore rehearsal, deletion receipt, or secure
erasure workflow.

References:

- `docs/DEPLOYMENT.md`
- `docs/REMOTE_PRODUCT.md`

### L2: Deferred While L0 Exists

These could differentiate Fern, but none should precede the L0 workflow:

- Whole-host wake through a durable external relay
- Explainable protocol-safe sleep blockers
- Portable agent-workstation export
- Private wakeable previews and artifacts
- Delivery to a physically sleeping host

These are already identified in `docs/REMOTE_PRODUCT.md`. They should
not be implemented before the phone-to-draft-PR path works.

### Later

- Enterprise SSO and SCIM
- Hostile multi-tenancy
- Kubernetes
- Multi-agent orchestration
- Multi-repository transactions
- General workflow builder
- Organization-wide policy and compliance controls

## Outside-In Journey Trace

### 1. Install And Update The Server

1. **User action:** Provision Ubuntu, install Git, Go, Docker and Tailscale,
   create users and directories, clone Fern, build a binary and image, edit
   secrets, install systemd, and configure Tailscale Serve.
2. **Owner:** Operator, systemd, Docker, Tailscale, and Fern CLI. No component
   coordinates the complete operation.
3. **Identity:** Host root, Docker-group `fern` user, and Tailscale account/device
   identity.
4. **Credential custody:** `/etc/fern/fern.env`, Tailscale-owned state, and the
   Docker socket. Fern and provider passwords do not expire automatically.
5. **Durable proof:** Installed binary, image, systemd unit, configuration, and
   operator-recorded checksums. No Fern installation record exists.
6. **Failure behavior:** Partial installation requires manual diagnosis.
   Image/config changes cause spec drift and require `fern down` then `fern up`.
7. **Recovery surface:** Shell commands, `systemctl`, `journalctl`, Docker CLI,
   and the runbook.
8. **Status:** Documented and partially implemented, not productized.
9. **Evidence:** Build and CI evidence exists; complete target-host installation,
   update, rollback, and reboot are untested.
10. **Leading products:** Managed agents remove host installation. Self-hosted
    platforms normally provide signed packages or an installer, health checks,
    migrations, and coordinated upgrades.

### 2. Pair A Phone Or Browser And Reconnect

1. **User action:** Manually enroll the phone in Tailscale, discover the Serve
   URL, obtain the shared Basic password, and open the official OpenCode V2 web
   UI proxied at `/`.
2. **Owner:** OpenCode owns the UI, session, configuration, and provider
   experience; Tailscale owns enrollment; Fern owns wake-aware authenticated
   proxying. No component yet owns proposed Fern device onboarding.
3. **Identity:** Tailnet member/device plus a shared Fern password.
4. **Credential custody:** Tailscale external state and a manually shared static
   password.
5. **Durable proof:** Tailscale device record only. Fern stores no paired-device
   record.
6. **Failure behavior:** Fern has no mobile reconnect state, offline command
   queue, or device recovery.
7. **Recovery surface:** Tailscale tools and manual password redistribution.
8. **Status:** Root UI proxying is the architecture. Device pairing, cookie
   gateway, notifications, and real-phone acceptance remain proposed/unproven.
9. **Evidence:** HTTPS origins are unit-tested; no real-phone test exists. Device
   pairing, a cookie gateway, and notifications are proposed, not implemented.
10. **Leading products:** GitHub Mobile starts Copilot sessions; Cursor offers
    iOS and Android PWA; Claude Remote Control provides QR/session pairing,
    short-lived credentials, reconnect, trusted-device revocation, and push
    notifications.

### 3. Authenticate A Provider And Select A Model

1. **User action:** Obtain an API key externally and manually add it to Fern's
   service environment.
2. **Owner:** External provider and OpenCode. Fern only forwards environment
   variables.
3. **Identity:** Provider account/API key; no task-scoped Fern provider identity.
4. **Credential custody:** `/etc/fern/fern.env`, systemd environment, and Docker
   container environment. Rotation is manual and may require recreation.
5. **Durable proof:** Configuration presence, not successful authentication or
   model entitlement.
6. **Failure behavior:** Expired keys, quota exhaustion, model removal, and
   provider outages surface as upstream errors; Fern records no classified
   failure or retry.
7. **Recovery surface:** Edit the environment, inspect logs, and restart or
   recreate manually.
8. **Status:** Delegated without onboarding, quota, model, or budget integration.
9. **Evidence:** No provider-backed lifecycle acceptance test.
10. **Leading products:** Copilot and Cursor expose model selection and account
    billing; Cursor requests a spend limit; Codex surfaces repository
    environment and account-managed usage settings.

### 4. Install GitHub Access And Select A Repository

1. **User action:** Currently clone the repository manually with an unspecified
   credential.
2. **Owner:** Operator and Git CLI. The proposed GitHub App broker does not
   exist.
3. **Identity:** Whatever Git credential the operator arranges; no immutable
   installation or repository identity.
4. **Credential custody:** Unspecified. Unsafe token forwarding would expose it
   to the container.
5. **Durable proof:** A host directory, potentially with `.git`; Fern only
   verifies that it is a directory.
6. **Failure behavior:** Revocation, repository rename or transfer, wrong origin,
   token expiry, and ambiguous clone state are unreconciled.
7. **Recovery surface:** Manual Git commands.
8. **Status:** Documented proposal; unsupported integration.
9. **Evidence:** No GitHub or clone tests.
10. **Leading products:** Codex, Jules, Cursor, and Copilot use account OAuth or
    App installation and explicit repository selection, retaining repository
    identifiers and permissions.

### 5. Clone And Prepare The Development Environment

1. **User action:** Clone, install dependencies, configure private registries,
   initialize submodules/LFS, and warm caches manually or ask the unrestricted
   agent to do so.
2. **Owner:** Operator, repository scripts, and OpenCode.
3. **Identity:** Package-registry, submodule, LFS, and private-network
   credentials, all currently unspecified.
4. **Credential custody:** Usually container environment or manually created
   files; no scoped secret lifecycle.
5. **Durable proof:** Files in the bind mount or OpenCode volume. No setup
   version, status, or log record.
6. **Failure behavior:** Setup can partially mutate the workspace with no
   resumable phase or classified failure.
7. **Recovery surface:** Container logs and manual shell access.
8. **Status:** Unsupported product boundary; arbitrary shell execution is not an
   integration.
9. **Evidence:** Lifecycle tests only verify bind-mount and volume persistence.
10. **Leading products:** Codex has setup/maintenance scripts and cache
    invalidation; Cursor has Dockerfile/snapshot environments and build history;
    managed products expose setup logs and secret settings.

### 6. Submit And Cancel OpenCode Work

1. **User action:** Send a live OpenCode protocol request through the proxy.
2. **Owner:** Fern transports it and OpenCode owns the live session. Fern has no
   durable lifecycle/external-effect shadow record.
3. **Identity:** Shared Basic authentication, not a user/device/task principal.
4. **Credential custody:** Static Fern password.
5. **Durable proof:** None in Fern. OpenCode may persist completed conversation
   state.
6. **Failure behavior:** Lost requests and responses are ambiguous. Retrying can
   duplicate intent. Cancellation does not prove upstream termination.
7. **Recovery surface:** Reconnect to OpenCode and infer state manually.
8. **Status:** Live proxying implemented; durable command semantics unsupported.
9. **Evidence:** Wake coalescing and request/pause exclusion are tested; durable
   delivery is not.
10. **Leading products:** Managed agents create durable session/task records
    visible from web/mobile, with status, logs, follow-ups, and bounded
    execution.

### 7. Disconnect While Work Continues

1. **User action:** Close the phone or lose connectivity.
2. **Owner:** OpenCode/provider determine whether execution continues; Fern only
   keeps the container alive while activity remains observable.
3. **Identity:** Existing OpenCode session.
4. **Credential custody:** Provider key remains in the container.
5. **Durable proof:** Completed OpenCode SQLite messages and working-tree
   changes; active streams and tools are process memory.
6. **Failure behavior:** A phone disconnect may be harmless, but OpenCode or
   container loss abandons active provider streams and tools.
7. **Recovery surface:** Reattach and inspect conversation/files.
8. **Status:** Assumed upstream behavior; not provider-tested.
9. **Evidence:** Simulator tests safe activity-based stopping, not real
   disconnected turns.
10. **Leading products:** Cloud agents run independently of clients. Claude
    Remote Control queues status during reconnect but documents its local
    process dependency.

### 8. Answer Questions And Permissions

1. **User action:** Remain connected through an OpenCode client and answer an
   upstream form or permission request.
2. **Owner:** OpenCode. Fern only detects pending forms and permissions.
3. **Identity:** Shared authenticated connection; no approval principal.
4. **Credential custody:** No Fern approval credential or signed decision.
5. **Durable proof:** No Fern approval record, question ID, answer, expiry, or
   audit event.
6. **Failure behavior:** A lost answer is ambiguous. Survival across OpenCode
   process loss is unproven by Fern, and Fern cannot recover unavailable
   upstream approval state.
7. **Recovery surface:** Reconnect and inspect upstream state if it is available.
8. **Status:** Idle blocking implemented; remote approval product unsupported.
9. **Evidence:** Unit tests prove permissions/forms prevent pause.
10. **Leading products:** Claude Remote Control and Jules send notifications
    when input is needed; mobile/web surfaces display and persist the
    interaction.

### 9. Inspect Logs, Diff, Tests, Artifacts, Previews, Or Take Over

1. **User action:** SSH to the host, run Fern CLI commands, or attach the
   OpenCode TUI.
2. **Owner:** Fern CLI exposes container logs/events; OpenCode owns conversation
   and terminal behavior.
3. **Identity:** Host account or shared Basic authentication.
4. **Credential custody:** No artifact-specific short-lived links.
5. **Durable proof:** Working tree, container logs, and local test outputs. Fern
   has no structured result manifest.
6. **Failure behavior:** Logs can be lost with rotation or container
   destruction; no artifact retention contract exists.
7. **Recovery surface:** `fern logs`, `fern debug events`, Git commands, and
   shell access.
8. **Status:** Operator diagnostics implemented; end-user results unsupported.
9. **Evidence:** CLI tests exist, but no browser/mobile artifact test.
10. **Leading products:** Codex presents summary and diff; Cursor provides logs,
    screenshots, video, artifacts, and remote desktop takeover; Devin exposes
    browser, IDE, and shell takeover.

### 10. Commit, Sign, Push, And Open A Draft PR

1. **User action:** Manually configure Git identity and credentials, commit,
   push, and invoke GitHub.
2. **Owner:** Currently operator/Git. No Fern publication owner.
3. **Identity:** Undefined author, committer, and GitHub actor.
4. **Credential custody:** Undefined; no host-only token broker or signing-key
   custody.
5. **Durable proof:** Local commit and remote branch/PR if manually created.
   Fern stores none of their identifiers.
6. **Failure behavior:** Token expiry, branch races, and lost push/PR responses
   are unreconciled.
7. **Recovery surface:** Manual Git/GitHub inspection.
8. **Status:** Unsupported; design document only.
9. **Evidence:** No automated publication test.
10. **Leading products:** Copilot, Cursor, Codex, Jules, and Devin allocate
    branches, push changes, and create or prepare pull requests under their
    source-control integration.

### 11. Handle CI, Review Feedback, And Conflicts

1. **User action:** Observe GitHub manually and send another live instruction.
2. **Owner:** No Fern component owns the loop.
3. **Identity:** GitHub reviewer/check actor and exact PR head are not correlated
   into Fern state.
4. **Credential custody:** No fresh GitHub installation-token lifecycle.
5. **Durable proof:** GitHub remains authoritative, but Fern stores no delivery
   ID, check run, comment cursor, or attempt.
6. **Failure behavior:** Events can be missed while the host sleeps; stale CI or
   comments can trigger incorrect work; conflicts have no policy.
7. **Recovery surface:** Manual GitHub inspection and a new ad hoc session.
8. **Status:** Unsupported.
9. **Evidence:** No CI/review integration tests.
10. **Leading products:** Copilot accepts `@copilot` PR comments and can start
    from failing Actions runs; Cursor accepts issue/PR mentions; managed control
    planes persist and reconcile events while workers are absent.

### 12. Rotate Secrets, Restrict Egress, Or Access Private Networks

1. **User action:** Edit environment files, restart or recreate the container,
   and configure host networking manually.
2. **Owner:** Operator, Docker, and external network systems.
3. **Identity:** Static provider keys, Fern password, and any manually supplied
   private credentials.
4. **Credential custody:** Host environment file and container environment; no
   secret version or lease.
5. **Durable proof:** Updated configuration only.
6. **Failure behavior:** Rotation can produce spec drift or interrupt work. No
   dual-key transition or rollback exists.
7. **Recovery surface:** Logs, configuration edits, and `fern down/up`.
8. **Status:** Manual and unsafe.
9. **Evidence:** Environment drift is tested; rotation and egress denial are
   not.
10. **Leading products:** Codex removes setup secrets before the agent phase and
    disables agent internet by default; Cursor exposes domain restrictions,
    secret settings, and private-network integration.

### 13. Idle Stop, Wake, Crash, Docker Restart, And Host Reboot

1. **User action:** Nothing for container idle stop/wake; manually recover failed
   reboot states.
2. **Owner:** Fern runtime, watcher, workspace manager, and Docker.
3. **Identity:** Authenticated requests trigger wake; pause checks authenticate
   to OpenCode.
4. **Credential custody:** OpenCode password remains static.
5. **Durable proof:** Docker state, persistent volume, and crash-consistent
   pause-intent file.
6. **Failure behavior:** Watcher loss fails safe by keeping compute running.
   Fern restart can reattach. OpenCode crash loses active work. Running-host
   reboot becomes failed.
7. **Recovery surface:** `fern status`, logs, `fern down`, and service restart.
8. **Status:** Container idle/wake implemented; active-work crash and reboot
   recovery unsupported.
9. **Evidence:** Strong unit/race tests and the single 13-scenario V2 Docker
   lifecycle suite. Historical legacy fixture results are superseded.
10. **Leading products:** Managed products replace failed workers from durable
    task state. Claude Remote Control reconnects after sleep/network recovery
    but still requires its local process to return.

### 14. Backup, Restore, Export, Delete, And Retain

1. **User action:** Stop Fern, archive four state locations manually, checksum
   them, and protect them. The runbook only advises a future restore rehearsal.
2. **Owner:** Operator, tar, and Docker.
3. **Identity:** Root/Docker access; backups may contain repository and service
   secrets.
4. **Credential custody:** Backup encryption and key rotation are external
   policy.
5. **Durable proof:** Tar archives and checksum file.
6. **Failure behavior:** No atomic whole-system snapshot or tested fresh-host
   restoration.
7. **Recovery surface:** No extraction or reconstruction procedure is supplied;
   the operator must design and rehearse one.
8. **Status:** Backup documented; complete restore, export, and retention
   unsupported.
9. **Evidence:** No automated restore rehearsal.
10. **Leading products:** Managed agents retain task and repository results in
    their control plane. Fern's self-hosted value requires stronger portable
    restore evidence than those products, not weaker evidence.

## Leading Product Boundary Comparison

### GitHub Copilot Cloud Agent

- Starts sessions from GitHub, GitHub Mobile, IDEs, API, CLI, integrations, and
  failing Actions runs.
- Uses GitHub identity and repository authorization.
- Runs in an ephemeral GitHub Actions environment.
- Creates a branch, commits, pushes, and can open one pull request.
- Supports follow-up through sessions and `@copilot` pull-request comments.
- Exposes model choice in supported entry points and accounts for Actions and AI
  usage.
- Limits a session to 59 minutes.

Source:
<https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent>

### OpenAI Codex Cloud

- Connects a GitHub account and selected repositories.
- Runs durable background tasks in isolated cloud environments.
- Supports setup scripts, maintenance scripts, environment variables, setup-only
  secrets, and container caches.
- Disables agent internet access by default and places egress behind a proxy.

## Smallest Complete Release

The smallest release that completes the target outcome is a constrained
one-user, one-host, one-GitHub-repository product. OpenCode is the user-facing
authority for sessions, UI, configuration, providers, models, questions,
permissions, and execution. Fern owns lifecycle and future device auth,
notifications, durable shadow operation records, tested publication, CI
reconciliation, and backup/recovery. It should not add multi-workspace scale,
general workflows, or novel whole-host wake.

Required release scope:

Fern additions in this release scope are proposed and unimplemented unless they
are explicitly identified above as implemented.

1. A packaged Linux installer with `init`, `doctor`, coordinated update and
   rollback, systemd setup, and automatic recovery after ordinary host reboot.
2. The official OpenCode V2 web UI, served by OpenCode at `/` and passed through
   unchanged by Fern's wake-aware authenticated proxy. Keep Fern controls under
   minimal `/fern/*` routes. Device pairing, a cookie gateway, revocation, and
   notifications are proposed release work. A narrow phone companion is only a
   fallback if the official UI fails mobile acceptance.
3. A Fern-owned SQLite control database containing workspace, device, lifecycle,
   publication, CI, artifact, and recovery shadow records, correlated to but not
   authoritative over OpenCode sessions.
4. Idempotent Fern-owned external operations with explicit delivery and outcome
   states; OpenCode remains authoritative for interactive session state.
5. One supported provider path configured and presented by OpenCode, with Fern
   limited to lifecycle policy and shadow outcome records rather than a second
   provider/model authority.
6. A private GitHub App integration for one selected repository, exact base-SHA
   checkout, and fresh short-lived installation tokens.
7. A declared repository support profile: setup script, setup-only secrets,
   persistent cache, Git LFS, and same-installation submodules. Unsupported
   repository features must fail preflight before a task starts.
8. Deterministic Git identity, one Fern branch per task, exact-commit push, and
   one draft PR. Signing may be explicitly unsupported in the first profile,
   but the policy must be visible.
9. Mobile views for conversation, questions, permissions, diff, test result,
   bounded logs, and selected artifacts.
10. Poll-based GitHub reconciliation for the exact PR head, CI failures, review
    comments, and conflicts, with a strict attempt and budget cap. A public
    webhook relay is not required for the first release.
11. Separated provider, setup, registry, and Git publication credentials.
    GitHub credentials must remain host-only; setup secrets must not remain
    available during agent execution.
12. Automated encrypted backup, checksum verification, and a destructive
    fresh-host restore acceptance test.
13. One real end-to-end acceptance test that starts on a phone, disconnects,
    answers an approval, receives a tested draft PR, processes one CI/review
    follow-up, reboots the host, and restores the workspace onto a clean host.

That is the release boundary. Everything else is either L1 hardening after this
path works, L2 differentiation, or later enterprise scope.
