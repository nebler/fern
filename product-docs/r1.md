# Fern Outside-In Product Audit

> Historical audit. See [`product-docs/README.md`](./README.md) before using any
> finding as current product or implementation guidance.

> Post-audit update (2026-08-16): Fern now has process-local one-time phone
> pairing, `/fern/*` landing/readiness routes, `fern init`, `fern doctor
> --phone`, and an explicit host-only draft-PR publication prototype. Historical
> findings below describe the audited snapshot; durable device identity,
> GitHub App onboarding, notifications, and real-phone acceptance remain open.

Audit date: 2026-08-16

## User Outcome

> From my phone, connect a private repository, ask an agent to make a change,
> let it work while I disconnect, answer any questions or permissions, inspect
> the result, and receive a tested draft pull request. Later, handle CI failures
> or review feedback, survive sleep and reboot, and restore the workspace after
> host loss.

## Verdict

Fern cannot currently complete this outcome.

The furthest supported journey is:

> An operator manually provisions a trusted Linux host, pre-clones a
> repository, and exposes Fern through externally configured Tailscale Serve.
> Fern can proxy the released OpenCode V2 server, including the official web UI
> that OpenCode serves at its origin root, and can idle-stop and wake the
> OpenCode container while retaining the worktree and OpenCode data volume.

Fern cannot provide a supported path from a phone to a tested draft pull
request. The official OpenCode UI has not passed phone acceptance, and there is
no device pairing, repository authorization, durable Fern shadow-operation
record, GitHub credential broker, setup contract, mobile result acceptance,
PR publisher, CI/review loop, reboot-safe recovery, or verified
fresh-host restore.

This is accurately acknowledged in `README.md` and
`docs/REMOTE_PRODUCT.md`.

The V2-only architecture direction is not implementation evidence. Device
pairing, a browser cookie gateway, notifications, tested publication,
attach-existing-service mode, and real-phone validation are proposed or
unperformed, not implemented.

Status terminology used below:

- **Implemented**: First-party executable Fern behavior exists.
- **Documented**: A manual procedure or design exists without implementation.
- **Delegated without integration**: An external product may provide behavior,
  but Fern has no onboarding, state, or recovery contract around it.
- **Assumed**: Fern relies on behavior without proving or exposing it.
- **Cannot support**: The current product surface cannot perform the step.

## Priority Classification

### L0: Outcome Blockers

1. The official OpenCode UI has no real-phone acceptance evidence, and Fern has
   no device pairing or cookie gateway.
2. No durable, idempotent Fern shadow record for lifecycle, cancellation, or
   external side effects correlated to an OpenCode session.
3. No GitHub installation, repository picker, or exact-SHA clone.
4. No safe Git identity, branch allocation, push, or draft PR creation.
5. OpenCode provider/model onboarding is not validated through Fern, and Fern
   has no lifecycle budget or real-provider acceptance test.
6. No deterministic project setup, private dependency, cache, or verification contract.
7. No durable question, permission, audit, or notification flow.
8. No mobile result record for diffs, tests, logs, or artifacts.
9. No CI/review reconciliation or bounded follow-up.
10. Running workspaces do not recover automatically after host or Docker restart.
11. No automated and verified fresh-host restore.
12. No supported installation, update, compatibility check, or rollback path.

### L1: Unsafe, Unreliable, or Painfully Manual

1. `fern attach` can derive a plaintext remote URL from a modified
   `proxy.listen`; only explicit `-url` receives the non-loopback HTTPS check.
2. Provider and arbitrary workspace secrets enter Docker's inspectable
   environment and are readable by repository code, tests, hooks, dependencies,
   and tools.
3. The container has unrestricted internet, LAN, tailnet, and private-service
   egress with no destination policy or audit.
4. Credentials cannot rotate live; environment changes require container
   destruction and recreation.
5. Authentication is one long-lived shared password with no device revocation,
   expiry, rate limit, or audit identity.
6. Git LFS, submodules, commit signing, private registries, credential helpers,
   and cache reset semantics are undefined.
7. Runtime status does not explain task progress or most sleep blockers.
8. Logs have no task correlation, product retention policy, or mobile access.
9. Backup encryption, off-host replication, deletion, and retention are manual.
10. No terminal write lease or safe human takeover protocol exists.

### L2: Deferred Until L0 Is Closed

These are possible differentiators, not current recommendations:

- Whole-host wake through an external coordinator.
- Private wakeable preview and artifact URLs.
- Explainable protocol-aware sleep blockers.
- An owner-exportable complete agent-workstation bundle.
- Rich browser terminal takeover and recordings.

### Later

- Enterprise SSO, SCIM, and organization policy.
- Hostile multi-tenancy.
- Kubernetes and multi-cloud scheduling.
- Multiplayer sessions.
- Multi-agent orchestration.
- General workflow automation.

## Additional Security Finding

`fern attach` applies different transport validation depending on how the target
is supplied:

- Explicit `fern attach -url ...` rejects non-loopback HTTP at
  `cmd/fern/attach.go`.
- Implicit `proxy.listen` conversion always creates `http://...` and accepts
  non-loopback addresses at `cmd/fern/attach.go`.
- `LoadAttach` does not perform the full `fern up` listener validation at
  `internal/config/config.go`.

A modified configuration can therefore make the official client connect to a
remote plaintext origin and disclose Basic credentials. This contradicts
`docs/ARCHITECTURE.md`.

**Classification: L1 now; release-blocking once Fern offers a supported remote client.**

## Smallest Complete Release

The smallest credible release is a single-user, one-host, one-repository
appliance that exposes OpenCode's official V2 web UI unchanged. OpenCode remains
the user-facing authority for sessions, UI, configuration, providers, models,
questions, permissions, and live execution. Fern owns lifecycle and, when
implemented, device authentication, notifications, durable shadow operation
records, tested publication, CI reconciliation, and backup/recovery. It should
contain only:

Fern additions in this release scope are proposed and unimplemented unless they
are explicitly identified above as implemented.

1. **Supported appliance lifecycle**
   `fern init`, `doctor`, install, pinned update, backup-before-update, health
   verification, rollback, and reboot-safe systemd/Docker reconciliation.

2. **The official OpenCode browser surface**
   Reverse proxy the released server's embedded UI unchanged at `/`, including
   wake behavior. Reserve only minimal `/fern/*` routes for Fern controls. A
   pairing and cookie gateway, revocable device credentials, and notifications
   are proposed release work, not current behavior. A narrow phone companion is
   a fallback only if the official UI fails real-phone acceptance.

3. **One durable Fern shadow-operation state machine**
   Correlate lifecycle, publication, CI, and recovery operations to OpenCode
   session/message IDs without replacing OpenCode's session authority. Persist
   idempotency, cancellation intent, outcomes, and bounded attempts only where
   Fern performs an external side effect.

4. **One GitHub App per appliance**
   Manifest onboarding, selected-repository installation, immutable
   repository/base-SHA recording, and host-only short-lived installation
   tokens.

5. **One explicit environment contract**
   A versioned setup command, setup-only private-registry secrets, timeout,
   logs, completion marker, persistent cache, and cache reset. Submodules and
   LFS must either pass acceptance tests or fail preflight with a specific
   unsupported-feature message.

6. **One supported OpenCode provider path**
   Provider onboarding, model selection, configuration, and provider errors stay
   in OpenCode. Fern may enforce lifecycle budgets and record shadow outcomes,
   but must not introduce a second provider authority. A real-provider
   disconnect test remains required.

7. **One OpenCode lifecycle adapter**
   Correlate Fern shadow operation IDs to OpenCode sessions/messages, observe
   questions and permissions without replacing their UI, deliver proposed
   notifications, and restart a failed attempt from durable work rather than
   claim mid-stream recovery.

8. **One result contract**
   Changed files, rendered diff, commands/tests with exit status, selected
   logs, completion summary, and authenticated downloadable artifacts.

9. **One safe publication path**
   Deterministic bot commit identity, Fern-owned branch, no force-push or
   default-branch push, host-brokered credentials, exact-SHA reconciliation,
   and one draft PR.

10. **One bounded follow-up loop**
    Poll GitHub rather than requiring public webhooks, correlate checks/reviews
    to the recorded head SHA, notify the user, and allow a bounded user-approved
    follow-up for CI failure, review feedback, or conflict.

11. **One recovery format**
    Encrypted off-host backup of the control database, worktree/Git objects,
    OpenCode data, configuration, artifact metadata, and exact versions, plus
    automated restore onto a clean Ubuntu host.

12. **One mandatory acceptance test**
    From a real phone: pair; select a private test repository; submit a task;
    disconnect; answer a permission; reconnect; inspect diff/tests; receive a
    draft PR; induce CI failure and review feedback; run follow-ups; idle-stop
    and wake; reboot; destroy the host; restore on a fresh host; verify the same
    task, branch, PR, and completed work.

Do not add whole-host wake, rich previews, multiple workspaces, terminal
takeover, multi-agent workflows, or enterprise identity until that acceptance
test passes end to end.
