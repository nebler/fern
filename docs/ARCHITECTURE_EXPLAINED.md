# fern, Explained From Scratch

A standalone architectural tour: what fern is, why its boundaries sit where
they sit, which module owns what, where Docker begins and ends, and how work
flows through the system. Written architecture-first — component names over
line numbers. Companion documents:

- `docs/ARCHITECTURE.md` — the normative, implementation-derived contract
  (authoritative where they disagree).
- `product-docs/code-review-p0-p1.md` — independent review of the spine.
- `product-docs/r5–r7` — strategy and market context.

---

## 1. The One-Sentence Model

**Fern treats OpenCode as a volatile compute process that may vanish at any
instant without notice, and builds a durable, journaled, fail-closed control
plane around that assumption.**

Everything in the codebase — the two listeners, the pause-intent files, the
SQLite trigger web, the delivery coordinators — is a consequence of this one
stance. Most agent tooling treats the harness as the application and the infra
as plumbing; fern inverts that. The harness is the disposable part.

Three corollaries drive every boundary:

1. **Absence of evidence is not evidence of anything.** An idle session is not
   a finished task. An empty inbox is not a successful prompt. A stopped
   container is not necessarily a deliberate stop. Fern never converts silence
   into a conclusion.
2. **Intent is recorded before effect.** Before stopping a container, fern
   writes a pause-intent file. Before pushing a branch, the publication
   coordinator commits a `push_started` phase. If the process dies mid-effect,
   the journal distinguishes "we meant to do this" from "something exploded."
3. **Fern mints its own identities.** Tasks carry caller-chosen OpenCode
   session/message IDs generated by fern at admission time. Retries reuse the
   exact IDs, so a duplicate submission is detectable and idempotent instead of
   silently duplicated.

## 2. What Exists, In One Paragraph

Fern is a single Go binary (`cmd/fern`) that supervises one ephemeral Docker
workspace running `opencode2 serve`. It exposes two HTTP surfaces on loopback —
a remote/device listener published privately through Tailscale Serve, and a
local operator listener. Inbound traffic wakes the workspace when it is asleep
and proxies through once it is healthy. When nothing has happened for a while,
fern stops or freezes the container — but only after proving, twice, that
nothing is active. On top of that lifecycle kernel sits a durable task pipeline:
a paired phone submits a coding task, fern admits it into a SQLite journal, delivers
it to OpenCode exactly once, observes it conservatively, seals the result only
with explicit user authority, and optionally verifies it with a fenced host-side
runner. The GitHub App publication reconciler is implemented, but no production
command creates its initial publication record. In workspace-`gh` mode, users or
the agent instead run ordinary `gh`/Git mutations directly. A paired phone can
submit, list, inspect, cancel, and authorize snapshot sealing.

## 3. Trust Model And Threat Posture

Before any diagram makes sense, the trust assumptions have to be explicit,
because every boundary is drawn against them.

| Principal | Standing |
| --- | --- |
| The single owner | Trusted root. Fern is single-host, single-owner software; there is no multi-tenancy anywhere. |
| Host OS + Docker daemon | Privileged boundary. Docker-group access is effectively root. Fern does not defend against it. |
| Repository code running inside OpenCode | Trusted-inside-the-workspace. Fern constrains the container (uid/gid, cap-drop, PID/memory/CPU limits, no-new-privileges) but explicitly does **not** claim hostile-code isolation. |
| OpenCode server | Trusted to do agent work, **distrusted as an oracle**. Its API responses are characterized, not assumed; its silence proves nothing. |
| Tailnet | Transport boundary. Tailscale provides reachability and TLS; it does not provide fern identity. |
| Paired phones | Capability holders. Digest-backed device grants, revocable, expiring; never equivalent to operator authority. |

Two postures follow:

- **Fail closed everywhere.** Unknown route ⇒ treat as work (wake-inducing,
  idle-invalidating). Unknown activity state ⇒ defer the pause. Ambiguous stop
  outcome ⇒ leave intent pending, classify as unresolved. Malformed SSE event ⇒
  invalidate eligibility. Every "I don't know" resolves to the more expensive,
  safer answer.
- **Authority is narrow and non-interchangeable.** A checkout's `origin` URL
  cannot select which GitHub repository gets touched. A browser `Host` header
  cannot select the effective public origin. A request body cannot choose the
  verification command. Actor identity comes from authentication snapshots,
  never client headers. Each of these rules exists because the alternative is a
  confused-deputy hole.

## 4. Topology: Two Listeners And A Private Edge

```text
      phone / laptop (tailnet)                 local operator CLI
               │  HTTPS via Tailscale Serve          │ loopback :8081
               ▼                                     ▼
    ┌─────────────────────────┐          ┌─────────────────────────┐
    │  remote listener :8080  │          │ operator listener :8081 │
    │  paired-device grants   │          │  Basic-auth policy      │
    └───────────┬─────────────┘          └───────────┬─────────────┘
                └──────────────┬─────────────────────┘
                               ▼
              request admission (observe / read / work)
                               ▼
       coalesced wake ──► docker resume or create ──► health + auth probes
                               ▼
             attested endpoint (loopback port, generation-stamped)
                               ▼
           opencode v2 serve — pinned image digest, unprivileged UID
                               ▼
      unbuffered SSE / streaming reverse proxy back to the client
```

**Why two listeners?** Because the remote and operator surfaces need
irreconcilable credential models. The remote edge serves a browser (cookies,
CSRF, Fetch-Metadata checks) and must never see backend or operator Basic
credentials. The operator surface serves the official CLI and admin routes with
Basic auth and must never be reachable off-host. Both Basic credentials are
rejected on the remote listener *before any wake*, so probing the public edge
cannot even spin compute up. Fern strips inbound `Forwarded`/`X-Forwarded-*`
and regenerates them from trusted configuration, so a malicious client cannot
smuggle routing authority.

**Why loopback-only backend publication?** The workspace container publishes
its port bound to `127.0.0.1` with an ephemeral port. The only way in is
through fern, which means admission control and wake semantics are
unbypassable. Docker's dynamic port assignment also gives each backend
incarnation a fresh endpoint, which is what makes stale-endpoint detection
meaningful.

## 5. The Modules And Their Contracts

Go enforces an acyclic package graph. The useful architectural grouping is:

```text
shared leaves: evidence · gitref · jsoncanon · task
host ports:    config · control · runtime(Docker) · registry · githubapp · opencodeapi
policy kernel: workspace · watch · workspacegithub
durable core:  taskstore · taskapi · taskresult · verification
coordinators:  taskdelivery · taskexecution · taskresultcoord
               taskverification · taskpublication · taskpublicationcoord
ingress:       proxy
root:          cmd/fern imports and composes the system
```

The boundaries are intentionally not a perfectly horizontal stack. For example,
`taskapi` depends on the result authorizer interface, and `proxy` embeds the task
API. The important rule is that external effects are behind narrow interfaces
and the composition root is the only place that selects production authority.

### 5.1 `internal/runtime` — the Docker port

**Responsibility:** translate between Docker's reality and fern's vocabulary.
It owns the *words* the rest of the system uses: `Spec` (desired workspace),
`Endpoint` (host:port of a live backend, explicitly marked non-persistable),
`Observation` (a classified snapshot of container reality), five `State`s
(absent, provisioning, running, paused, failed), and the `IntentStore`
interface.

**Depth:** this is a deep module. Callers see four verbs —
`EnsureRunningObserved`, `ReconcileStartup`, `Pause`, `Status` (+ destroy/
logs/exec helpers) — hiding inspection, label verification, fingerprinting,
volume management, rollback logic, and state classification.

**What it deliberately leaks:** a little Docker flavor survives on purpose.
`Observation.Frozen` (Docker's freezer-pause flag), `SpecFingerprint`, and
`ExitCode`/`OOMKilled` exist because downstream *policy* needs those raw facts.
The leak is documented vocabulary, not accident — fern's whole safety story
depends on distinguishing frozen from stopped.

**What it refuses to do:** decide anything. Runtime reports classified facts;
policy lives in `workspace`. It also never talks to OpenCode — health probing
is the one exception, and even that is a pure HTTP check with negative
authentication tests, not agent interaction.

### 5.2 `internal/workspace` — the policy kernel

**Responsibility:** own the lifecycle of exactly one workspace. Admission of
requests, coalescing of wakes, serialization of mutations, endpoint
attestation, the pause barrier, and the quiesced fence used by the task
system.

**Its interface is small and its interior is dense** — the definition of a deep
module. Callers see: `AcquireRequest` (get a target + release func),
`EnsureRunning`, `ReconcileStartup`, `Pause`, `AcquirePaused`,
`AcquireQuiesced`, `InvalidateEndpoint`, `LastWakeTrace`, `Close`. Inside are
two mutexes with a strict nesting rule, a capacity-one lifecycle token, a
coalescing channel, and generation counters.

**Key internal concepts:**

- **Admission gate.** Read/work requests hold an admission lease for their
  entire proxied lifetime; observe requests (the SSE tap) do not. The gate is
  also the pause barrier's first lock: pausing closes admission so no new work
  can start mid-shutdown-check.
- **Coalesced wake.** All simultaneous wakers share one `wakeCall`; a canceled
  caller does not cancel the shared wake. One goroutine performs the mutation;
  everyone waits on its done-channel.
- **Endpoint attestation + generations.** An endpoint is published only after
  the runtime attests: running state, valid immutable image ID, loopback
  endpoint. Each publication bumps a monotonically increasing generation.
  Invalidation compares (endpoint, generation) pairs, so stale failure news can
  never discard a newer working endpoint.
- **The two-pass pause barrier.** Before stopping, fern requires admission
  closed **and** two consecutive all-idle passes across six activity surfaces
  (sessions, shells, PTYs, permissions, forms, questions). Why two passes?
  Because OpenCode exposes six unrelated endpoints with no atomic snapshot;
  activity beginning during pass one is caught by pass two while no new request
  can slip in (admission is closed).
- **The quiesced fence (`AcquireQuiesced`).** A stronger variant used by result
  sealing: close admission, take the lifecycle token, require the caller's own
  observation twice plus an all-idle pass each time, stop compute, and hold the
  fence until released — guaranteeing no container writer mutates the checkout
  while Git evidence is collected.

### 5.3 `internal/watch` — the eyes

**Responsibility:** answer one question continuously — "is the agent doing
anything right now?" — without ever trusting a possibly-stale answer.

Three cooperating pieces:

- **`Stream`** (event.go): a spec-correct SSE parser. Multi-data-line frames
  joined per the SSE spec, comment lines skipped, bounded frame size, content-
  type enforcement. Boring and correct.
- **`StreamController`** (controller.go): owns the *connection*. Reconnects
  with backoff, and stamps every observation with a monotonically increasing
  **connection epoch**. When a connection dies and a new one forms, events from
  the old epoch are rejected as stale.
- **`Supervisor`** (supervisor.go): a single-goroutine actor owning the
  activity model — connected? busy-seen? which sessions are active? It reduces
  observations to three timer actions (arm/cancel/none) and fires the pause
  callback when eligibility holds. Because one goroutine owns the model, there
  is not a single lock in the reduction logic.

**Why epochs are necessary, not gold-plating:** OpenCode's SSE stream is
volatile *by contract* — disconnections lose events, there is no replay. A
dying old connection's "disconnect" event arriving late could otherwise cancel
a legitimately armed pause timer of the new connection, or vice versa: stale
"busy" from a previous backend incarnation could keep a dead workspace awake
forever. Epoch comparison kills both failure modes. The reviewer's instinct
("this smells like a workaround") was tested and the scheme survived scrutiny.

**The subtle policy worth knowing:** a user request arriving during armed idle
does *not* cancel eligibility — it re-arms the timer. Rationale: otherwise a
final browser poll after idle would prevent pause forever, since no further
session-status transition is required. The Manager's authoritative two-pass
check remains the real safety net; the timer is just the trigger.

### 5.4 `internal/proxy` — the front door

**Responsibility:** turn raw HTTP into classified intents; enforce identity,
origin, and CSRF policy; route `/fern/*` control-plane traffic; proxy
everything else upstream without buffering.

Request classification is deliberately conservative:

| Intent | Matches | Behavior |
| --- | --- | --- |
| Observe | `GET /api/event` (no upgrade) | no admission lease; stream survives until pause disconnects it |
| Read | `GET/HEAD /api/health`, `/api/session/active` | admission lease, but does not invalidate idle policy |
| Work | everything else, incl. WebSocket upgrades | full lease + invalidates idle evidence |

Unknown routes default to **work**, so a future OpenCode endpoint can never
silently bypass wake/idle semantics.

Other responsibilities: pairing codes (256-bit, five-minute TTL, digest-stored)
exchanged for 30-day `__Host-fern_device` cookies; persisted issuance and
attempt limits; per-route CSRF tokens for cookie-authenticated mutations with
Fetch-Metadata enforcement (Basic-auth mutations exempt); reserved-cookie
stripping so OpenCode can never mint fern identity; and the reverse proxy itself
running with `FlushInterval: -1` —
immediate flush, no response buffering — which is why SSE streams cleanly
through it.

### 5.5 `internal/registry` — durable doubt

Two tiny stores: a **host-local lease** preventing two `fern up` processes from
mutating the same workspace, and the **pause-intent store** — atomic-replace
JSON files recording `BeginPause → CommitPause` (or shutdown intent with an
expiry window), read back with paranoid hygiene (O_NOFOLLOW, hardlink count ==
1, mode 0600, size caps). This store is what upgrades Docker's ambiguous
"container exited" into fern's classifiable "paused (intentional)" versus
"failed (unexplained)."

### 5.6 `internal/config` — the bouncer

Strict YAML (unknown fields rejected), canonical-form validation for origins
and listen addresses, environment-forwarding allowlists (`ANTHROPIC_API_KEY`,
`OPENAI_API_KEY`, `OPENCODE_PASSWORD` eligible; `GH_TOKEN`/`GITHUB_TOKEN`/
control secrets refused — checked by key, by alias expansion, and by
post-expansion equality), and task-policy validation (bounded durations, shell-
free argv, executables outside the repository). Configuration errors are
returned, never panicked.

### 5.7 The persistence split — two stores on purpose

| | Legacy JSON control store | SQLite task store |
| --- | --- | --- |
| Holds | device grants, coarse workflows, legacy publications | tasks, attempts, receipts, events, results, manifests, verifications, publications, seal requests |
| Guarantees | atomic file replace + fsync | WAL, foreign keys, **trigger-enforced state machines**, migration checksums |
| Fate | shrinking; unwired publisher lane | the durable heart |

The task store deserves emphasis: transitions are enforced by SQL triggers —
terminal states are immutable, revisions increment monotonically, cancellation
invariants hold, and direct-SQL tamper attempts are rejected. The application
layer *cannot* produce an illegal transition even if it wants to. This is the
database-as-state-machine pattern, and it is the reason the coordinators above
it can be relatively simple: the store refuses what the code might mistakenly
attempt.

## 6. Where Docker Plays A Role — Precisely

Docker is fern's compute substrate, and the relationship is deliberately
narrow. Enumerated:

**What fern asks Docker to do**

1. **Container lifecycle** — create, start, stop (graceful, 10 s), unpause
   (defensively), remove. Never kill -9 first; never force-remove a started
   workspace (data volume retention kicks in the moment OpenCode has started).
2. **Port publication** — one port, bound to loopback, dynamically assigned.
   Fern reads the binding back from inspect and treats it as the endpoint.
3. **Resource envelope** — memory limit, CPU quota (2 cores), PID ceiling
   (512), `init`, all capabilities dropped, `no-new-privileges`, no restart
   policy, writable root FS.
4. **Volumes** — one durable OpenCode data volume (survives destroy) plus an
   optional GitHub-config volume in workspace-gh mode; both labeled and
   verified for ownership.
5. **Immutable image identity** — fern inspects the *actual* image ID (not the
   tag) and carries it through every attestation. Tags lie; digests don't.
6. **Spec fingerprint** — a SHA-256 over the desired spec (name, image, repo
   path, resources, env **keys**, mounts) stored as a container label; recomputed
   and compared on every resume. Note the keys-only choice: secret *values*
   never land in `docker inspect`-visible labels; value drift is caught later by
   live comparison.
7. **Exec** — one bounded escape hatch: run the pinned `gh` binary inside the
   attested container (workspace-gh base resolution), with deadline validation,
   output caps, and exit-code proof.
8. **Logs** — streamed for diagnostics.

**What fern does with the answers** — the classification function. Docker's
raw state is ambiguous; fern resolves it against the intent store:

| Docker says | Intent says | fern concludes |
| --- | --- | --- |
| running, not paused | — | `running` |
| paused (frozen) | — | `paused` (defensive; fern thaws before mutating) |
| exited | committed pause / shutdown-in-window | `paused` |
| exited | pending (crash mid-stop?) | `provisioning` — unresolved, retry carefully |
| exited | none | `failed` |
| OOM-killed / dead | — | `failed` |
| created | committed pause | `paused` |
| created | none | `provisioning` |

**What fern pointedly does NOT use Docker for**

- **No restart policies.** Fern is the supervisor; Docker restarting things
  behind its back would corrupt state classification.
- **No Docker healthchecks.** Fern probes actively and *negatively* — it
  requires missing credentials to get 401, wrong credentials to get 401, correct
  credentials to succeed, and the SSE stream to connect. A silently-unauthenticated
  backend is rejected, not adopted.
- **No Docker networking features.** Loopback binding only; no user networks,
  no published-on-0.0.0.0, ever.
- **No compose/swarm/orchestration.** Single host, single workspace, one writer
  enforced by a filesystem lease.
- **No `docker checkpoint`.** Fern's domain pause is a committed intent plus the
  configured suspension effect: graceful stop in `idle.mode: stop`, or cgroup
  freeze in `idle.mode: freeze`. Frozen observations are thawed before
  stop/destroy transitions that require a running process.

The honest cost of the current stop-based pause: ~2.8–3.1 s cold wake, because
OpenCode boots from zero. The freezer conversion (`idle.mode: freeze`)
suspends via the cgroup freezer instead — processes stay resident, wake is an
unpause measured in milliseconds, and the intent journal still applies (a
frozen container that later exits — host reboot, daemon restart — classifies
as paused rather than failed). The state machine needed no structural change:
the classifier already understood frozen-with-intent.

## 7. Where OpenCode Plays A Role — And Where It Can't Be Trusted

OpenCode v2 (pinned: `0.0.0-next-17444`, digest-verified in CI) supplies the
agent loop, the UI, sessions/tools/files, provider calls, permissions/forms,
and its SQLite storage. Fern consumes a characterized subset:

- **Prompt admission is idempotent and durable.** `POST /api/session/{id}/prompt`
  accepts caller-chosen message IDs and returns the same receipt on duplicate
  submission. This single property is what makes fern's exact-once delivery
  possible: retries carry identical bytes and IDs, and conflicts are detectable.
- **The inbox** lists durably enqueued work and supports cancel — fern uses it
  to prove what is pending and to delete proven-undelivered items during
  cancellation.
- **Everything else is characterized, not assumed.** The contract harness
  (`integration/opencode-contract`) pins the exact image digest and black-box
  verifies thirteen properties per build: same-ID/same-body retry stability,
  restart history survival, permission/form process-epoch scoping, interrupt
  semantics, max prompt size. Blocked properties are printed, not papered over.

**The structural limitations fern designs around:**

1. **SSE is volatile by contract** — disconnects lose events; no Last-Event-ID
   replay. Hence epochs (watch) and polling adapters (completion detection).
2. **`/wait` is a stub** — no blocking completion primitive exists.
3. **Permissions/forms are process-epoch scoped** — a pending approval can
   vanish across an OpenCode restart while the underlying work continues. Fern
   records `input_required` but never assumes an answer survived; durable
   approvals live in fern's own schema roadmap.
4. **No generic terminal-success proof** — the root product blocker. An idle
   session is not a succeeded prompt. Fern therefore fails closed: attempts
   reach `running`/`input_required` and stop; success requires either explicit
   user authorization (the seal path) or a future authoritative observer built
   on the v2 cursor-replayable event log.

The consequence is philosophical as much as technical: **fern supervises
outcomes, not conversations.** It holds receipts, not beliefs.

## 8. Lifecycle Narratives

### 8.1 Life of an HTTP request

1. Arrives on a listener; identity resolved (device cookie or Basic) *before*
   any wake. Unauthorized ⇒ 401, zero Docker contact.
2. Classified: observe/read/work.
3. Work/read acquire an admission lease (observe skips). If the manager is
   closing ⇒ refusal.
4. Cached endpoint valid? Serve immediately. Otherwise join the coalesced wake:
   one goroutine takes the lifecycle token, calls
   `runtime.EnsureRunningObserved`, which inspects (ownership labels, fingerprint,
   actual spec), resumes or creates, waits for authenticated health, clears the
   pause intent, and returns an attested observation.
5. Manager attaches/reconnects the SSE watcher to the new endpoint (new epoch),
   publishes endpoint+imageID with a bumped generation.
6. `httputil.ReverseProxy` streams the exchange unbuffered; release runs at
   response end, decrementing admission.
7. Meanwhile the request's work intent invalidated idle evidence; the supervisor
   re-arms the pause timer only after observing busy→idle drains again.

### 8.2 Life of a pause

Supervisor sees busy→idle drain at the current epoch ⇒ arms the idle timer ⇒
fires ⇒ drains queued observations (late disconnect cancels) ⇒ still eligible ⇒
calls `Manager.Pause`:

```
beginPause        — close admission; refuse if requests in flight
acquireLifecycle  — exclusive mutation token
pauseWhileHeld    — Status() → refuse provisioning; clear endpoint if already
                    stopped; else TWO all-idle passes over six surfaces
pauseRuntime      — runtime.Pause: BeginPause intent → configured Docker stop
                    or freeze effect → CommitPause intent
release           — reopen admission; next request pays a cold start or thaw
```

Failure releases the in-process fences. An ambiguous external pause effect keeps
its durable intent pending, so later classification refuses to guess whether
compute is safely dormant.

### 8.3 Life of a durable task (phone → sealed result)

1. **Admission.** Phone POSTs with an `Idempotency-Key`; fern resolves the base
   ref through GitHub numeric authority, generates the OpenCode session/message
   IDs itself, and creates task + attempt + receipt + actor snapshot in ONE
   SQLite transaction — committed *before* any wake.
2. **Delivery.** A coordinator claims the attempt under a lease and walks a
   monotonic phase journal: `claimed → session_create_started → session_ready →
   prompt_started`. Each phase commits before its effect. Lost responses are
   reconciled by reading back exact IDs; a same-ID/different-body conflict is a
   hard error, never a silent resend.
3. **Execution observation.** Positive evidence only: active session ⇒
   `running`; live permission/form ⇒ `input_required`. Anything else stays
   open-ended. Cancellation commits a fence first, then interrupts or deletes
   proven-undelivered inbox items.
4. **Sealing.** A paired user previews one exact clean Git snapshot under a
   paused fence, then submits that same tuple with an idempotency key. The
   durable request is revalidated and recollected before an immutable result is
   written; the attempt becomes `superseded`, not falsely `succeeded`.
   Verification may then run — host-owned, shell-free, descriptor-pinned,
   process-group contained, with clean commit state proven before and after.
5. **Publication forks by authority mode.** Workspace-`gh` users/agents may run
   direct GitHub mutations, outside Fern's effect journal. App-broker transport
   can safely reconcile `push_started → push_observed → pr_create_started →
   published`, but no production API prepares its initial journal row.

There is a current lifecycle defect between steps 4's halves: preview/request
leaves compute paused, while asynchronous completion asks for a quiesced fence
that currently requires an already-running target. A seal may wait for unrelated
upstream traffic to wake the workspace; this needs a real-manager integration
fix rather than documentation optimism.

### 8.4 Life of a crash

Startup replays the world in order: listeners bound first (side-effect-free
failure), lease acquired, Docker reconciled without waking dormant workspaces,
interrupted provisioning repaired, publication journals drained before serving.
Shutdown reverses it: graceful HTTP drain → force-close tracker → coordinators
stop → shutdown intent recorded only on real signals → manager closed (its wake
goroutines owned until done) → stream stopped → Docker client last, leaked
deliberately if the manager timed out rather than risk racing owned goroutines.

## 9. State Machines Everywhere

Fern's states, and who enforces them:

| Machine | States | Enforced by |
| --- | --- | --- |
| Workspace runtime | absent / provisioning / running / paused / failed | classification function over Docker + intents |
| Task | queued → running → input_required → … → completed/failed/canceled | SQLite triggers + coordinator transactions |
| Attempt delivery phase | claimed → session_create_started → session_ready → prompt_started | monotonic journal columns |
| Verification | prepared → running → succeeded / failed / recovery_required | trigger immutability; rerun prohibited after ambiguity |
| Publication | none → push_started → push_observed → pr_create_started → published | journal-fenced coordinator |
| Seal request | pending → claimed → completed / rejected | immutable approved tuple + expiring claim revision |
| Pause intent | none → pending → committed (or shutdown, expiring) | atomic intent files |

Design rule: **illegal states are unrepresentable.** The database rejects
terminal overrides and revision regressions; the intent files reject
post-hoc relabeling; the manager's gates make the racy interleavings
structurally unreachable. Where a state genuinely cannot be determined
(`uncertain`, `recovery_required`, pending intent), it is *represented* rather
than guessed away — uncertainty is a modeled outcome, not an error path.

## 10. Concurrency Ownership Map

Every long-lived goroutine has a named owner and a bounded lifetime:

| Goroutine | Owner | Bounds |
| --- | --- | --- |
| HTTP servers ×2 | errgroup on serviceCtx | Shutdown → tracked force-close |
| Supervisor actor | errgroup | ctx; owns its model lock-free |
| Delivery/execution/result/verification/publication coordinators | errgroup | ctx; serialized by per-coordinator runMu |
| Coalesced wake | Manager | done-channel; Close awaits it; 90 s budget |
| Stream generation + per-attempt parser | StreamController | operations token serializes; done awaited |
| Verification reaper | one runner invocation | process-group teardown |
| Legacy publication worker | No production goroutine; package retained but unwired | n/a |

Locks: `wakeMu` and `admissionMu` in the Manager with a single legal nesting
direction (admissionMu→wakeMu), documented on the type. Tokens: the lifecycle
channel and the controller's operations channel serialize mutations. Channels
do double duty as broadcast (close-to-release-all waiters) and as fences
(requestsDone/pauseDone). Contexts thread everywhere; detached
`context.Background()` appears only in cleanup paths, always time-boxed, and is
pinned by dedicated tests.

Cancellation guarantees: caller cancel releases a waiter but not the shared
wake; service shutdown drains servers before closing the manager; manager close
drains admission → pause → lifecycle → wake before the Docker client closes;
on timeout, the client is intentionally leaked rather than raced.

## 11. State Inventory — Who Knows What

| Kind | Contents |
| --- | --- |
| Memory only | cached endpoint + generation, closing flags, admission counters, activity model, last wake trace |
| Disk (fern-owned) | host lease; pause-intent files; JSON control store (devices/workflows/legacy pubs/operator credential ID); persisted pairing limiter; SQLite task journal; GitHub App credentials |
| Docker volumes | OpenCode data; optional persistent workspace-`gh` config and credentials |
| Derived from Docker, never persisted | container existence/state, dynamic port, actual image ID, spec-fingerprint label |
| Duplicated by design | cached endpoint vs inspect truth (generation-invalidated); desired-spec fingerprint vs recomputed (drift detector); JSON store vs task journal (documented compatibility split) |

Rule of thumb: anything Docker can change behind fern's back is *never*
persisted — it is re-derived and re-attested on every wake.

## 12. Security Architecture In Five Moves

1. **Split ingress.** Operator authority never transits the remote edge; remote
   identity is capability cookies with digest-only storage, revocation that
   cancels in-flight requests, and expiry deadlines inherited by proxied
   contexts.
2. **Negative probing.** Endpoints are adopted only after proving they reject
   missing and wrong credentials — defending against a silently-unauthenticated
   backend, not just a broken one.
3. **Header hygiene.** Inbound forwarding chains stripped; outbound regenerated
   from trusted config; reserved cookie names stripped from upstream responses.
4. **Narrow authority.** Numeric GitHub IDs over URLs; in App mode,
   repository-scoped short-lived tokens and askpass files invisible in argv,
   logs, and evidence; in workspace-`gh` mode, an explicit trusted-workspace
   credential boundary; verification commands host-owned and structurally
   incapable of being chosen by clients.
5. **Tamper-evident local state.** Intent files and control store enforce
   private dirs, no symlinks, single hardlink, bounded sizes, atomic replace +
   fsync — cheap, filesystem-native resistance to casual tampering.

Named residual risks are kept in `docs/SECURITY.md`: unencrypted App and
workspace-`gh` credentials, trusted-workspace credential exposure, operator
forms without device-style tokens, and incomplete physical acceptance — each
tracked, none hidden.

## 13. Observability: What Counts As Proof

Fern separates three evidentiary tiers:

- **Volatile signals** — the SSE stream, health probes, wake timings. Useful
  for scheduling; never cited as proof of outcomes. (Wake traces now emit a
  per-phase millisecond waterfall via `fern debug wake`.)
- **Structured logs** — state transitions with elapsed times, wake durations
  over 100 ms, classified failures with sanitized causes.
- **Durable evidence** — the task journal: immutable actor snapshots, ordered
  event cursors, bounded sanitized JSON with SHA-256 digests, byte-count-not-
  bytes output capture, stored unit prices beside computed costs (planned for
  metering), manifests of exact object IDs. Sensitive payloads (prompts,
  credentials, subprocess output) are excluded from evidence by construction.

The audit principle: a claim is only as strong as the journal entry that would
survive a crash alongside it.

## 14. Known Gaps And Open Questions

Honest architecture includes its holes:

1. **User-seal lifecycle** — preview/request leaves compute paused but the
   asynchronous coordinator requires an already-running target. Completion can
   stall until unrelated traffic wakes it. Preview is also a side-effecting GET.
2. **Phone replay and status** — the UI creates a new idempotency key for every
   invocation and exposes no coherent seal rejection, verification, or brokered
   publication status after an accepted command.
3. **Generic terminal-success observer** — unbuilt. Automatic completion still
   requires a future durable authoritative OpenCode primitive; idle, empty
   inbox, and volatile event history remain insufficient.
4. **Brokered publication admission** — transport and reconciliation exist, but
   no production API prepares the initial publication journal row.
5. **Workspace-`gh` binding validation** — a new immutable binding may be stored
   before the first live credential/repository check.
6. **Failed-vs-paused conflation on unhealthy starts** — a container that starts
   but never passes the health probe currently receives a *committed* pause
   intent and presents as dormancy. Deliberate anti-crash-loop behavior or bug —
   decision pending; fix is a distinct intent flavor or documented expectation.
7. **Durable approvals** — no approvals table/API; permission answers die with
   the process epoch.
8. **Notifications** — absent entirely; the phone learns only by asking.
9. **Multi-workspace** — singular by declaration throughout (one Manager, one
   stream, one config shape). Honest simplicity, real ceiling.
10. **Legacy publisher lane** — implemented, tested, wired out of production;
   awaiting formal retirement or revival.
11. **Physical acceptance** — real TLS/WSS behavior, reboot/restore drills,
   tailnet ACL-negative tests remain operator-run exercises.

## 15. Glossary

| Term | Meaning |
| --- | --- |
| **Pause** (domain) | Compute suspended under committed Fern intent, by graceful stop or configured cgroup freeze. |
| **Frozen** | Docker's observed freezer-cgroup state; thawed before incompatible lifecycle mutations. |
| **Generation** | Monotonic counter for attested backend endpoints (manager-level). |
| **Epoch** | Monotonic counter for SSE connections (watcher-level). Stale either ⇒ ignored. |
| **Seal** | Atomically bind immutable Git/OpenCode identity and Git evidence either to proven execution success or an exact user-authorized snapshot. |
| **Quiesced fence** | Admission closed + lifecycle held + two clean observations + compute stopped, retained through evidence collection. |
| **Intent** | Durable pre-effect record converting ambiguous external state into classified state. |
| **Workspace-gh / App-broker** | The two GitHub authority modes: agent-owned `gh` in-container vs fern-brokered installation tokens. |
| **Exact-once-attempted** | Delivery guarantee: retries reuse identical IDs/bytes; duplicates detectable, conflicts fatal. |
