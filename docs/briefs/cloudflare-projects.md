# Cloudflare projects on Fern

Status: built 2026-11-10 (`lab/check.sh cloudflare`), with onboarding from a thread; hiding Local needs T3's app, which Fern doesn't ship.

## Why
A small site on Astro and Cloudflare (Workers, D1 for data, R2 for pictures) is the kind of project a person with a slow laptop builds through T3 on a Fern server. The goal: a Cloudflare repository runs, reverts and deploys from a thread with nothing to set.

## Tried (VPS, 2026-11-10, `nebler/nutri-games`)
- Astro 7 with `@astrojs/cloudflare` 14 and wrangler 4 build in a box (`astro build` 2 s), and `wrangler dev` (workerd) serves the page and an API route under gVisor.
- With `mise.toml` (Node 22, pnpm 10) and a `services.yaml` running `astro dev`: golden build 72 s, then a page through the preview in 0.17 s.
- A first try hung at wake: its `package.json` had a `dev` script and no dependencies yet, so the guessed `pnpm run dev` had no `astro` to run. Not a bug in the guess, which installs before it starts the dev server.
- pnpm 10.34 no longer reads `pnpm.onlyBuiltDependencies` from `package.json`; it goes in `pnpm-workspace.yaml`, or workerd's and esbuild's install scripts don't run.
- A project T3 cloned from GitHub lands in T3's home. That was `/home/node/<repo>`, in the image's root and outside the pool, which cost three things, found 2026-11-11 by running a thread end to end: every update replaces the image, so the first rebuild deleted `nutri-games` and T3's project pointed at nothing; a worktree's box got no git folder (the store gives it only for `repos/` and `projects/`), so git and `cloudflare_connect` failed in it; and backups didn't take it. T3's home is now `projects/` (`lab/check.sh t3`). A Local thread there ran Claude in T3's own service, unboxed: `fern-claude` refused sessions only in `repos/` and `projects/`. Fixed: it refuses a session anywhere that isn't a Fern workspace (`lab/check.sh t3`).

## Built
1. **Detecting a Cloudflare project** (`setup.IsCloudflare`): `wrangler.jsonc`, `wrangler.json` or `wrangler.toml` at the root, or a dependency on `wrangler`, `@astrojs/cloudflare`, `@cloudflare/vite-plugin` or `@opennextjs/cloudflare`. A Worker with no framework (`"dev": "wrangler dev"`) gets wrangler's flags and port 8787 from the guess; a framework on Cloudflare keeps its own dev server, which runs workerd.
2. **Claude is told** (`fern-init`'s hint): D1, R2 and KV are emulated in `.wrangler/state`, with no account; that data is snapshotted with every turn; deploys happen by pushing from T3; no `wrangler deploy` or `wrangler login` in the box.
3. **Local Cloudflare state is the environment's.** `.wrangler/state` is in the workspace, so a turn's snapshot takes it and a revert brings it back, as with Postgres. `lab/check.sh cloudflare` writes a D1 row and an R2 object through the preview, snapshots, deletes them, restores, and reads them back.
4. **Deploys by push.** Cloudflare's Workers Builds deploys a push to `main` and gives other branches a preview URL; T3's threads push through the GitHub App. Fern adds no code here, only the hint's line and the README.
5. **Opt-in Cloudflare MCP for the agent box.** `FERN_CLOUDFLARE_TOKEN_FILE=… install.sh root@HOST` (or `install.sh cloudflare` on the server, the token on stdin) keeps the token in `/etc/fern/cloudflare.env`, root only. The daemon reads it at each agent's start, and only for a repository that deploys to Cloudflare adds Cloudflare's MCP server (`https://mcp.cloudflare.com/mcp`, the token as its bearer token) to Claude's `--mcp-config`, or OpenCode's settings, in the agent box. The box that runs the repository's code, the workspace, goldens and snapshots never get it (`lab/check.sh cloudflare` greps for it). `fern doctor` says whether it is set.

## Onboarding from a thread (built 2026-11-10)
Goal: a person's only steps are the logins no one can take for them. Tried by hand on `nebler/nutri-games` first: live at its `workers.dev` URL, and a branch got its own preview URL.
1. **Deploy from GitHub Actions, not Cloudflare's GitHub app.** Cloudflare's Git integration needs its GitHub app and dashboard clicks; a workflow (`wrangler deploy` for `main`, `wrangler versions upload --preview-alias <branch>` for other branches) needs only a file and a repository secret, both of which Fern can set. The first deploy also creates the KV namespace Astro's sessions bind, unasked.
2. **One token, from a pre-filled link.** Cloudflare's token form takes `permissionGroupKeys` in its URL: Workers Scripts, D1, R2 and KV edit, Account Settings read (README). The server keeps it (`install.sh cloudflare`).
3. **Claude's skills.** The box image has Cloudflare's own skills ([cloudflare/skills](https://github.com/cloudflare/skills), Apache-2.0, pinned: `cloudflare`, `frameworks-on-cloudflare`, `cloudflare-app-bootstrap`, `wrangler`, `cf-cli`, `workers-best-practices`, `durable-objects`, `web-perf`) and Fern's `fern-deploy` (`images/skills/`). In a Cloudflare repository fern-init links them into Claude's folder, outside the workspace, and takes them away in another. `fern-deploy` adds the workflow, fixes pnpm's build approvals, creates production D1 with the MCP server, calls `cloudflare_connect`, and tells the person to push. Cloudflare's skills assume the agent may `wrangler deploy` and `wrangler login`; the hint and `fern-deploy` say not to, and their MCP config (OAuth in a browser) isn't used: the daemon adds the server with the node's token.
4. **`cloudflare_connect`,** a tool on Fern's MCP server (with a Cloudflare token and a GitHub App on the node): the daemon reads the repository's `origin` with git in the box (the node can't resolve a T3 worktree's git folder; git by its full path, as the workspace's tools come first on the box's `PATH`), and sets its `CLOUDFLARE_API_TOKEN` secret through the GitHub App, sealed with the repository's key (`golang.org/x/crypto/nacl/box`), with a token that may only write secrets. Claude never sees the value. The App needs *Secrets: write*; T3's pushes of the workflow need *Workflows: write*, which tokens ask for and drop if the App lacks it.

## Run end to end (2026-11-11)
A real thread through T3 on the VPS, in `nebler/nutri-games`: what is this and where is it, build a second game, put it online. Claude named the preview link, built and tested the game with `animate`, `emil-design-eng` and `mobile-native` on, and asked before going further. What it found:
- T3's home lost the clone at the update, and its worktrees' boxes had no git folder (Tried, above). Fixed.
- Cloudflare's MCP server refused the token, "Insufficient scope": since 2026-11-09 it reads `/user` and `/accounts` when a user's token connects, so the token also needs *User Details: Read*, which the pre-filled link didn't ask for. The README says to add it; the link's key for it isn't in Cloudflare's docs.
- Both one-time permissions failed late, when "put it online" ran. `fern doctor` now asks Cloudflare whether the token reads its account and its user, and GitHub which permissions each account gave the App, and names the one to add.
- With deploys already set up, Claude called `cloudflare_connect` again and said the site couldn't go online when it failed. `fern-deploy` now checks the workflow's history first and ends with the one step left: commit and push in T3.
- A wake took 34 s before the first page: pnpm 7 s to say nothing was to install, Astro 22 s to start (CPU, in the box). The guess, and `nutri-games`, skip pnpm when the lockfile is the one installed (`cmp` with `node_modules/.pnpm/lock.yaml`). The same site starts in 7 s outside gVisor, on the same server, which has no KVM.
- The wake no longer waits for the site: its service has `listen: tcp:4321`, so it starts at the first connection (wake 34 s → 0.2 s; the first page after a wake 27 s, once, the next 0.2 s). The preview couldn't start it, as fern-init held the port on localhost and the preview comes to the box's address: a previewed port is now held on every address. The guess's dev server starts the same way.
- Every Claude waited 25 s at its start for Fern's own MCP server, in every repository: a new thread's first turn, and each message after Claude's idle stop (30 s). Claude's newer MCP client opens a stream to listen on when a server says its tool list may change, which the SDK's server says by default, and Fern's endpoint holds every answer until its call ends, so the stream never opened and Claude gave up after 25 s. Fern's server now says its list doesn't change: `claude -p` in a box 29 s → 5.4 s, a new thread's first turn through T3 33 s → 8.4 s. The lab's baseline for it was from before Claude's update.
- `lab/t3-run.sh cloudflare` is that run as a script, on `lab/cloudflare-repo`: the preview link, a D1 row through a revert, and the deploy skill.
- T3 gives Claude its own MCP server at an address on the node's loopback, which Claude's box couldn't reach: it showed as failed. Now the box's fern-init answers at that address and passes `/mcp` on through the daemon (architecture: T3's own MCP server). A first try rewrote the address in Claude's arguments; T3 sends it in the session's stream, so there was none to rewrite. Checked in a real thread: Claude listed the project's threads with `t3_thread_list`.

## Skill packs (built 2026-11-10)
For a person who doesn't read code, what Claude knows matters more than what it can run. Packs are folders of skills in the box image (`/usr/local/share/fern/skills/<pack>/<skill>`, sources pinned and checked, licenses kept beside them), plus an optional `CLAUDE.md` that goes into the hint while the pack is on. A pack is on when the node turns it on (`/etc/fern/skills`, read at every wake and passed as `FERN_SKILLS`; `safety` without the file) or when Fern detects it (`cloudflare`): one list per server, on for every thread. A per-repository switch in `services.yaml` was built and removed the next day: it reached other threads only after a merge, and was a second place to look. fern-init links the active packs' skills into Claude's folder and removes the rest. Each skill's description sits in Claude's context every turn, so packs stay small.
- `beginner`: a note, no skills: plain words, the preview link, errors fixed not shown, ask before big or public steps.
- `safety`: Fern's `site-safety` and Cloudflare's `turnstile-spin`; `/security-review` before the first deploy.
- `design`: Emil Kowalski's `emil-design-eng`, `animate` and `mobile-native`. His four review and audit skills were cut: they overlap, and each skill's description costs context on every turn.
- `engineering`: Dillon Mulroy's `coding-standards` and `install-anti-slop` (Oxlint rules: a linter reviews what the person can't), Matt Pocock's `codebase-design` and `diagnosing-bugs`.
- An Astro site's agent also gets Astro's docs MCP server (no login), as the daemon adds Cloudflare's.

Left out, and why: Anthropic's `frontend-design` (would pull against Emil's), Stageshow (marketing mock-ups), Trail of Bits' skills (for auditors), Dillon's older `cloudflare-skill` (Cloudflare's own replaces it), Astro's repository skills (for Astro's contributors).

## Not built: hiding Local
The Local / New worktree picker is in T3's app, not its server: the app chooses the mode (`resolveNewThreadEnvMode`, `packages/shared/src/projectSettings.ts`) from the server's `defaultThreadEnvMode`, which Fern sets to `worktree`, and the project's own default, which is unset. A server patch can't hide the choice. What Fern has: the default, and `fern-claude` refusing the session with a message naming New worktree. The fix belongs upstream: a server setting T3's app honours, such as "worktrees only", that removes Local from the picker.
